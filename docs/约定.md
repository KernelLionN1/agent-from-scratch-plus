# 执行约定

> AI 编码助手在执行任务时必须遵守的规则。

## 编码规范

1. **中文注释**：每个代码块必须有详细中文注释，说明这句代码的作用——这是教学项目，不是生产代码。
2. **Java 类比**：Python 概念用 Java 类比辅助理解（dict→Map, `__init__`→构造器, 模块级函数→static 方法）。
3. **有状态用类**：需要管理状态时用类 + `__init__`；无状态逻辑用模块级纯函数。
4. **刻意踩坑标注**：代码中预设的坑点用注释明确标注 "【踩坑】"，说明踩了什么坑、为什么保留、Day3 如何修复。

## 执行流程

1. **执行前**：读取 `AGENTS.md` 了解项目导航和当前状态。
2. **执行中**：按 `docs/计划/02-计划.md` 的阶段顺序推进，不跳阶段。
3. **执行后**：更新 `docs/执行/02-执行.md`（执行日志，记录做了什么、遇到了什么问题）。
4. **阶段完成**：生成 `docs/学习/` 下的学习指南（概念讲解 + 代码解读 + Java 对照 + 动手实验）。

## Git 规则

1. **不立即推送**：每完成一个阶段不提交+推送，等用户学完、加上自己的问题和实验改动后，统一推。
2. **Git 身份**：`nith / nitianhua@outlook.com`，SSH 认证到 `github.com/KernelLionN1`。
3. **分支隔离**：Day1 在 `01-solo-agent-handcode`，Day2 在 `02-multi-agent-handcode`，互不干扰。
4. **推送命令**：HTTPS 不可用，必须用 SSH 推到 `upstream` 远端：
   ```bash
   git push upstream <分支名>
   ```
5. **提交信息规范**：遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/)：
   ```bash
   git commit -m "类型(范围): 主题"
   ```
   | 类型 | 用途 |
   |------|------|
   | `feat` | 新功能（新增 Agent、新增工具等） |
   | `fix` | 修复缺陷 |
   | `docs` | 文档（学习指南、计划、注释等） |
   | `refactor` | 重构（改结构不改行为） |
   | `test` | 测试（新增/修改验证脚本） |
   | `chore` | 杂务（依赖、配置等） |
   | `style` | 格式调整 |

   示例：
   ```bash
   git commit -m "feat(agents): add PlannerAgent with task decomposition"
   git commit -m "docs(学习): add Day2 Phase2 learning guide"
   git commit -m "fix(bus): prevent message duplication in receive()"
   ```

## 踩坑策略

- Day1 和 Day2 的所有阶段都要保留刻意踩坑点（已在 `docs/计划/02-计划.md` 中标注）。
- 坑点在代码中用 "【踩坑】" 注释标注位置和说明。
- Day3 统一修复所有坑点，不提前修。
- 弱 system prompt、eval 不校验、全局 agent 污染等 Day1 遗留坑也在 Day3 统一处理。

## 环境约束

| 约束 | 说明 |
|------|------|
| WSL (Ubuntu 22.04) | 无 sudo 权限 |
| uv 缓存 | 部分文件属 root，需 `UV_CACHE_DIR=/tmp/uv-cache` 绕过 |
| GitHub 推送 | HTTPS 超时不可用，仅用 SSH（端口 443） |
| .venv 跨平台 | Linux .venv 不能在 Git Bash/PowerShell 用，必须进 WSL |
