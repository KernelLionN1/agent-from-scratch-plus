## 一、先理解：为什么需要循环？

阶段一你能做的事：

```python
response = llm.chat(messages, tools=tools)   # 问一次 LLM
if response["tool_calls"]:                    # LLM 说用工具
    result = execute_tool(...)                 # 你手动执行
    # ← 到这里就停了！结果没还给 LLM
```

问题：**工具执行完就结束了，LLM 不知道工具结果，无法基于结果给出最终答案。**

阶段二的循环解决了这个问题：

```python
while True:
    response = llm.chat(messages, tools=tools)
    if response["content"]:          # LLM 直接回答了 → 结束
        return response["content"]
    if response["tool_calls"]:       # LLM 想调工具
        执行工具 → 结果塞回 messages  # → 下一轮 LLM 能看到结果
```

---

## 二、核心概念：ReAct 模式

ReAct = **Rea**soning + **Act**ing（推理 + 行动），来自 2022 年 Google 的论文。

### 对比：有无循环的区别

```
没有循环（阶段一）：
  LLM 输出 "我需要调 calculator" → 你手动执行 → 结束

有循环（阶段二）：
  LLM 输出 "调 calculator" → Agent 执行 → 结果反馈 LLM
    → LLM 分析结果 → "还需要调 search_knowledge" → Agent 执行
      → LLM 综合两个结果 → "答案是 X，来源于..."
```

就像你和同事讨论问题：你说一句话，他做事，告诉你结果，你再说下一步。来回多轮，最终得出结论。

### Agent 循环的每一步拆解

```
messages = [
    {"role": "system", "content": "你是助手"},
    {"role": "user",   "content": "123*456=?"},
]
       ↓
┌─ while True ──────────────────────────────────────┐
│                                                    │
│  ① llm.chat(messages, tools)                       │
│     → LLM 返回: tool_calls = [calculator("123*456")] │
│                                                    │
│  ② 执行 calculator("123*456") → 结果 "56088"       │
│                                                    │
│  ③ messages 追加:                                  │
│     {"role": "assistant", "tool_calls": [...]}     │
│     {"role": "tool", "content": "56088"}           │
│                                                    │
│  ④ 循环回到 ①                                      │
│     → LLM 看到工具结果 "56088"                      │
│     → LLM 返回: content = "123×456 = 56088"         │
│     → 有 content，退出循环 ✓                        │
│                                                    │
└────────────────────────────────────────────────────┘
```

## 三、代码详解

### 3.1 ReActAgent 类的结构

```python
class ReActAgent:
    def __init__(self):
        self.llm = LLMClient()            # 依赖 1：会说话的嘴
        self.tools = get_tool_definitions() # 依赖 2：会干活的手
        self.system_prompt = "..."         # 行为规则
```

对应 Java：

```java
@Service
public class ReActAgent {
    @Autowired private LLMClient llm;       // 依赖注入
    private List<ToolDef> tools;            // 工具列表
    private String systemPrompt;            // 系统提示词
}
```

### 3.2 run() 方法 —— 核心循环

```python
def run(self, user_message: str) -> str:
    # 1. 构建初始消息 —— system 在最前面，user 在第二位
    messages = [
        {"role": "system", "content": self.system_prompt},
        {"role": "user", "content": user_message},
    ]

    # 2. 进入循环
    while True:                          # ← 坑点：没有最大轮次限制！
        response = self.llm.chat(messages, tools=self.tools)

        # 3. LLM 直接回复 → 退出
        if response["content"]:
            return response["content"]

        # 4. LLM 要调工具 → 执行并反馈
        if response["tool_calls"]:
            for tc in response["tool_calls"]:
                tool_args = json.loads(tc["arguments"])   # ← 坑点：无异常处理
                tool_result = execute_tool(tc["name"], tool_args)

                # 追加两条消息：LLM 的调用意图 + 工具的执行结果
                messages.append({"role": "assistant", "tool_calls": [...]})
                messages.append({"role": "tool", "content": tool_result, ...})
```

### 3.3 为什么追加两条消息？

这是 OpenAI 协议要求的格式：

| 消息 | role | 含义 |
|------|------|------|
| 第 1 条 | `assistant` | "我决定调 calculator，参数是 123*456" |
| 第 2 条 | `tool` | "calculator 执行完毕，结果是 56088" |

LLM 需要这两条消息才能把「调用意图」和「执行结果」关联起来（通过 `tool_call_id`）。

类比 Java RPC：第 1 条 = 请求日志，第 2 条 = 响应结果。缺任意一条，LLM 都不知道发生了什么。

### 3.4 消息列表的演变过程

以「计算 123*456」为例，messages 的变化：

```
初始：
  [system] [user: "123*456=?"]

第 1 轮后：
  [system] [user: "123*456=?"] [assistant: 调 calculator] [tool: 56088]

第 2 轮后：
  [system] [user: "123*456=?"] [assistant: 调 calculator] [tool: 56088]
  [assistant: "答案是 56088"]   ← 有 content，循环结束
```

注意：每一轮 messages 都在变长。当对话轮次很多时，messages 可能超过 LLM 的上下文窗口 → **阶段三要解决的截断问题**。

## 四、测试结果分析 —— 踩坑见效

### 测试 1：数学计算

```
LLM 说: "好的，我来帮你计算。"
→ Agent 认为这是最终答案，直接返回了
→ 实际上 LLM 根本没调 calculator
```

**根因**：系统提示词太温和（"请使用工具"），LLM 可以选择不用。更严格的提示词应该是"**当需要计算时，必须使用 calculator 工具**"。

### 测试 2：知识查询

```
LLM 调了 search_knowledge("DeepSeek 是什么")
→ 工具返回 {}
→ LLM 只好说 "让我再搜索一下" 然后放弃
```

**根因**：阶段一的搜索坑 + 缺乏重试/降级机制。工具失败时 LLM 不知道该怎么办。

### 学到的教训

| 问题 | 原因 | 解决方向 |
|------|------|---------|
| LLM 不调工具 | 提示词太弱 | 强化 system prompt：明确"必须"调工具 |
| 工具返回空就放弃 | 无重试逻辑 | Agent 应检测空结果，让 LLM 换关键词重试 |
| 潜在死循环 | 没有 max_iterations | 加轮次上限 + 超时保护 |

**这些在面试中都是高频问题："你的 Agent 不调工具怎么办？陷入循环怎么办？"**

self.system_prompt = (

## 七、下一步（阶段三预告）

现在的 Agent 有个致命问题：每次 `run()` 都重新构建 messages，**不记得之前的对话**。

阶段三要做的是：
- `src/memory.py` —— 对话记忆存储
- 多轮对话能力：上一轮说过的东西，下一轮还记得
- 上下文截断：messages 太长时自动裁剪
