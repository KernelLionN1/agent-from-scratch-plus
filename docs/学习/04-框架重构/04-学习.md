## 一、为什么 api.py 不需要改

阶段一二三重写了 `llm_client.py`、`agent.py`、`orchestrator.py`，但**接口完全兼容**：

```
api.py 依赖的接口          重写前（手搓）      重写后（LangChain）
───────────────────────────────────────────────────────────
create_agent()              ReActAgent(手搓)    ReActAgent(create_agent)
agent.run(msg)              while True 循环     _agent.invoke()
Orchestrator.run_serial()   if/else 控制流      StateGraph.compile().invoke()
Orchestrator.run_parallel() asyncio.gather      同一张图 + mode="parallel"
```

**核心原则：** 框架替换在 `src/` 内部完成，对 `api.py` 透明。这就是封装的意义。

## 二、全局异常处理器不受影响

```python
@app.exception_handler(asyncio.TimeoutError)  # 仍然生效
@app.exception_handler(Exception)             # 仍然生效
```

框架替换后异常类型没变——LLM 调用超时仍然是 `TimeoutError`，工具执行失败仍然是 `Exception`。

## 五、关键洞察：我们用的 vs LangGraph 真正的能力

**Day4 做的事：** 用 LangGraph 替代手搓 if/else，但图的边仍然是写死的——和普通工作流引擎没区别。

**LangGraph 真正的能力：LLM 自己决定路由。**

```python
# 我们做的（固定工作流）
graph.add_edge("planner", "coder")   # 永远走 coder，程序员决定的

# LangGraph 的设计意图（Agent 自主路由）
def llm_router(state):
    """LLM 根据当前状态决定下一步"""
    decision = llm.invoke(
        f"当前状态: {state}。下一步应该: 搜索、计算、还是直接回答？"
    )
    return decision  # ← LLM 决定走哪条边

graph.add_conditional_edges("agent", llm_router, {
    "search": "search_node",
    "calculate": "calc_node", 
    "respond": END,
})
```

**对比：**

| | Day4 做法 | LangGraph 原生能力 |
|---|---|---|
| 路由决定者 | 程序员（写死） | LLM（动态判断） |
| 流程灵活性 | 固定，预定义 | 动态，运行时决定 |
| 类比 | Spring StateMachine | 真正自主的 Agent |
| 适用场景 | 确定的业务流程 | 开放式的 Agent 任务 |

Day4 先把图用起来，自主路由留 Day5 探索。
