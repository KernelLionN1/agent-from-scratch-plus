## 一、先理解：为什么手搓版 Orchestrator 不够用？

Day2 的编排器长这样——所有控制流硬编码在 `if/else` 和函数调用里：

```python
def run_serial(self, requirement):
    plan = self.planner.execute(requirement)     # 步骤1
    code = self.coder.execute(plan)              # 步骤2
    review = self.reviewer.execute(code)          # 步骤3
    if with_fix:
        fixed = self.coder.fix_code(review)      # 步骤4（条件）
    return {"plan": plan, "code": code, ...}

def run_parallel(self, requirement):
    plan = self.planner.execute(requirement)
    subtasks = self._parse_subtasks(plan)
    codes = asyncio.run(...)                     # 并行分支
    combined = "\n\n".join(...)                  # 汇总
    review = self.reviewer.execute(combined)
    return {"plan": plan, "codes": codes, ...}
```

**问题：** 流程和代码绑死了。加一个步骤 → 改代码；换个顺序 → 改代码；想可视化流程 → 看代码猜。

**LangGraph 的区别：把流程从代码中抽出来，变成数据结构（图）。**

## 二、手搓 vs 框架：同一件事，两种写法

### 串行编排

```
手搓版（if/else 控制流）:
  planner.execute() → coder.execute() → reviewer.execute() → fixer.execute()
  步骤之间的顺序写在函数调用的先后顺序里

框架版（图声明）:
  graph.add_edge("planner", "coder")
  graph.add_edge("coder", "reviewer")
  graph.add_edge("reviewer", "fixer")
  步骤之间的顺序写在图的边上
```

**差别在哪？** 手搓版"改顺序"要改代码逻辑；图版"改顺序"改一条边的目标节点名。

### 条件分支

```python
# 手搓版
if state["with_fix"]:      # ← 条件判断嵌在业务代码里
    fixed = coder.fix_code(...)

# 框架版
def route(state):
    return "fixer" if state["with_fix"] else END  # ← 条件抽成路由函数

graph.add_conditional_edges("reviewer", route, {"fixer": "fixer", END: END})
```

### 一块代码跑全流程

```python
# 手搓版：每个路径一个函数
orch.run_serial(req)       # 串行
orch.run_parallel(req, n)  # 并行

# 框架版：同一张图，不同入参
app.invoke({"mode": "serial", "requirement": req})
app.invoke({"mode": "parallel", "requirement": req, "n_coders": 3})
```

## 三、为什么一张图替代了三个模块？

```
手搓版三个模块               框架版一个图         为什么能合并？
─────────────────────────────────────────────────────────
Orchestrator                 StateGraph          图的节点+边 = 控制流
  run_serial/run_parallel      add_node/add_edge
  在函数调用顺序里控制流程     在数据结构里声明流程

MessageBus                   State 自动传递      节点返回 dict → 自动注入下一个节点
  send/receive               不需要显式发送       不需要显式接收
  sender→receiver 手动       图的边决定流向

SharedState                  State dict          不需要加锁
  threading.Lock 保护        单线程执行（默认）   不需要乐观锁
  版本号+乐观锁              TypedDict 字段       声明式，编译期校验
```

**核心洞察：** 手搓版需要三个模块，因为它们要解决的问题不同——控制流、通信、共享状态。但在 LangGraph 里，这三个问题被统一为"节点返回 dict + 图编译执行"，一个概念解决三个问题。

## 四、State = 图的"入参+出参+中间变量"的集合

```python
class OrchestratorState(TypedDict):
    """图中每个节点都能读写的共享字典"""
    requirement: str      # 入参：用户需求
    plan: str             # Planner 写入 → Coder 读取
    code: str             # Coder 写入 → Reviewer 读取
    review: str           # Reviewer 写入 → Fixer 读取
    fixed_code: str       # Fixer 写入 → 最终输出
    mode: str             # 路由判断用

# 每个节点函数签名统一：
def coder_node(state: OrchestratorState) -> dict:
    code = generate_code(state["plan"])  # 读 plan
    return {"code": code}                # 写 code（自动 merge 回 State）
```

**不同业务 = 不同 State = 不同图。** 和 Java 里不同业务流程建不同 DTO 一样，天经地义。

## 五、Java 对照

| Python LangGraph | Java 等价 | 说明 |
|-----------------|----------|------|
| `StateGraph(State)` | `StateMachineBuilder<States, Events>` | 构建状态机 |
| `add_node("A", fn)` | `.state("A", action())` | 注册节点 |
| `add_edge("A", "B")` | `.source("A").target("B")` | 声明流转方向 |
| `add_conditional_edges` | `.source("X").choice(...)` | 条件分支 |
| `graph.compile()` | `.build()` | 编译成可执行对象 |
| `app.invoke(state)` | `machine.start()` + 事件驱动 | 执行 |

## 六、`compile()` 为什么存在

```python
graph = StateGraph(State)    # 声明：画图纸
graph.add_node("planner", fn)
graph.add_edge("planner", "coder")

app = graph.compile()        # 编译：把图纸变成执行引擎
app.invoke(state)            # 执行：按计划跑
```

**编译做了三件事：**

| 做的事 | 说明 | Java 对比 |
|--------|------|----------|
| 校验 | 所有边指向的节点都存在、无死循环 | 部分在 `build()`，部分在 `start()` |
| 拓扑排序 | 计算节点执行顺序 | `StateMachine.start()` 时做 |
| 缓存执行计划 | 一次编译，多次 invoke 复用 | 无等价——Java 状态机长期运行，不需要每次重建 |

**和 Java 的关键区别：** Java StateMachine 启动一次长期运行，拓扑排序放 `start()` 里无所谓。LangGraph 每次 `invoke()` 都是一次完整"启动→结束"，如果每次重算拓扑太浪费→`compile()` 缓存，`invoke()` 直接跑。

## 七、冒烟测试：为什么验证图结构

```python
def test_3d_graph_structure():
    graph = build_graph()
    assert len(graph.nodes) >= 5
```

不调 LLM，不调网络，只验证"图能正确编译"。防的是改代码时误删节点/边，导致后续 `invoke()` 炸在半路。等价于 Spring 的 `@Test void contextLoads()`——成本极低，能拦住低级错误。

## 八、并行：节点内并行 vs 图级并行

| | 节点内并行（当前） | 图级并行（Send API） |
|---|---|---|
| 图结构 | A→[B]→C | A→[B,B,B]→C |
| 图能感知分叉 | ❌ | ✅ |
| 单节点故障 | try/except 兜底 | 其他子图继续 |
| Java 类比 | ExecutorService.invokeAll | ForkJoinPool.fork/join |

并行结果的合并策略有三：机械拼接（字符串 join）、LLM 判断（调一次 LLM 选最优/融合）、规则合并（按长度/置信度排序）。合并是业务逻辑，不是框架的事。
