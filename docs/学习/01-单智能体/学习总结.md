# Day1 学习总结：原生单 Agent

> 分支：`01-solo-agent-handcode` | 总计 4 阶段

---

## 一、Day1 整体架构

```
用户
  ↓  HTTP POST /chat
FastAPI (src/api.py)
  ↓
ReActAgent (src/agent.py)
  ├── LLMClient    ← 调用 DeepSeek API
  ├── Tools        ← 计算器 + 知识查询
  └── Memory       ← 对话历史 + 截断
  │
  while True:        ← ReAct 循环
    Think → LLM 决定下一步
    Act  → 执行工具 / 直接回答
    Observe → 工具结果反馈
```

**核心设计：一个 Agent + 工具，LLM 自主决策何时调用工具、何时停止。**

---

## 二、阶段一：LLM 调用 + 工具注册

### 做了什么

```
LLMClient.chat(messages, tools) → {content, tool_calls, model, usage}
  封装 DeepSeek API，用 OpenAI SDK 兼容协议

工具注册表: { "calculator": fn, "search_knowledge": fn }
  calculator:       eval(expression) → 数值  【踩坑：直接 eval】
  search_knowledge: 关键词匹配 → dict         【踩坑：返回 dict 非字符串】
```

### 关键概念

| 概念 | 说明 | Java 类比 |
|------|------|----------|
| Function Calling | LLM 决定"我要调哪个工具，传什么参数" | RPC 远程调用 |
| Tool Schema | JSON Schema 描述工具入参 | API 文档的请求体定义 |
| `_parse_tool_calls()` | 从 LLM 响应提取 function_call | Response DTO → Domain Object |

### 踩坑

| 坑点 | 说明 |
|------|------|
| eval() 不校验 | 计算器直接 `eval(expression)`，恶意输入可执行任意代码 |
| 工具返回 dict | `search_knowledge` 返回 `{}` 而非字符串，LLM 无法消化 |
| 工具描述模糊 | tool description 写得太含糊，LLM 不知道该不该调用 |

## 三、阶段二：ReAct Agent 循环

### 做了什么

```
ReActAgent.run(user_message):
  messages = [system, user]
  while True:
    response = llm.chat(messages, tools)
    if response["content"]:
      return content          ← LLM 直接回答，停止
    elif response["tool_calls"]:
      for tc in tool_calls:
        result = execute_tool(tc.name, tc.arguments)
        messages.append({"role": "tool", "content": result})
      continue                ← 继续循环

Think → Act → Observe → Think → ... 直到 LLM 给出最终答案
```

### 关键概念

| 概念 | 说明 |
|------|------|
| ReAct 模式 | Reasoning + Acting，交替进行 |
| 思考-行动-观察 | LLM 思考 → 调工具 → 看结果 → 再思考 |
| 工具执行循环 | `while True` + LLM 自主决定何时停止 |
| max_iterations | 防止死循环的安全阀 |

### 踩坑

| 坑点 | 说明 |
|------|------|
| system prompt 太弱 | LLM 倾向于直接回答而不调用工具 |
| 不设最大轮次 | `while True` 可能死循环 |
| 工具结果无校验 | 工具失败时 LLM 拿到空结果/错误结果继续 |

## 四、阶段三：对话记忆 + 上下文截断

### 做了什么

```
ConversationMemory:
  _messages: list[dict]    ← 存储所有对话历史
  add_user/assistant/tool()  ← 追加消息
  get_messages(strategy)     ← 返回截断后的消息

三种截断策略：
  none:            返回全部（坑：超长会报错）
  sliding_window:  保留 system + 最近 N 条
  token_limit:     按字符数/4 估算 token，超限裁剪
```

### 关键概念

| 概念 | 说明 |
|------|------|
| 记忆持久化 | 跨 `run()` 调用的消息保留 |
| 上下文窗口 | LLM 能处理的最大 token 数 |
| 截断策略 | 滑动窗口 vs token 限制 vs 摘要压缩 |
| token 估算 | 简版：`len(text) / 4`，精确版需 tokenizer |

### 踩坑

| 坑点 | 说明 |
|------|------|
| 无截断 | 连续对话 20 轮会触发 API 上下文超限 |
| token 估算不准 | `字符/4` 对中文严重低估（中文每个字 ~1-2 token） |
| 简单截断丢上下文 | 只保留最近 N 条可能丢失关键早期信息 |

## 五、阶段四：FastAPI 封装

### 做了什么

```
FastAPI 应用:
  GET  /            ← 健康检查
  GET  /health      ← Agent 状态 + 工具数 + memory 统计
  POST /chat        ← 核心接口：发消息，返回 Agent 回复
  POST /chat/reset  ← 重置对话记忆
```

### 关键概念

| 概念 | 说明 | Java 类比 |
|------|------|----------|
| Pydantic Model | 请求/响应数据校验 | Bean Validation |
| TestClient | 进程内测试，不启网络 | Spring MockMvc |
| uvicorn | ASGI 服务器，启动 FastAPI | Tomcat / Netty |

### 踩坑

| 坑点 | 说明 |
|------|------|
| 全局 agent 实例 | `agent = ReActAgent()` 全局变量，并发请求共享 memory |
| 同步接口阻塞 | `def chat()` 非 `async def`，阻塞事件循环 |
| 无超时控制 | Agent 卡住时请求永久挂起 |

## 六、Day1 踩坑清单（9 项）

| # | 坑点 | 来源 | 后果 |
|---|------|------|------|
| 1 | eval() 不校验 | 工具安全 | 可执行任意代码 |
| 2 | 工具返回 dict 非字符串 | 工具设计 | LLM 无法消化 |
| 3 | system prompt 不强制使用工具 | Agent 行为 | LLM 口头答应但不调工具 |
| 4 | while True 无最大轮次 | Agent 循环 | 可能死循环 |
| 5 | 工具结果无校验/重试 | Agent 鲁棒性 | 空结果导致错误答案 |
| 6 | 无上下文截断 | 记忆管理 | 超长对话触发 API 报错 |
| 7 | token 估算严重不准 | 记忆管理 | 中文 token 低估 2-4 倍 |
| 8 | 全局 agent 实例共享 | API 并发 | 多用户 memory 互相污染 |
| 9 | 同步阻塞 + 无超时 | API 设计 | 请求永久挂起 |
