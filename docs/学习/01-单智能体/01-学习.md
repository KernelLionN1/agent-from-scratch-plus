## 一、先理解：什么是 AI Agent？

在你写代码之前，先搞清楚三个层次的区别：

```
┌─────────────────────────────────────────────┐
│  LLM (大语言模型)                             │
│  输入文字 → 输出文字                          │
│  只会"说话"，不会"做事"                        │
│  例：问 "1+1=?" → 回答 "2"（它算出来的）       │
└─────────────────────────────────────────────┘
                    ↓ 加上工具
┌─────────────────────────────────────────────┐
│  LLM + Function Calling（函数调用）           │
│  LLM 可以"指挥"外部工具干活                     │
│  例：问 "1+1=?" → LLM 说 "调 calculator"       │
│       → 程序执行计算器 → 结果返回 LLM           │
└─────────────────────────────────────────────┘
                    ↓ 加上循环
┌─────────────────────────────────────────────┐
│  Agent（智能体）                              │
│  LLM + 工具 + 循环 = 自主行动                  │
│  思考 → 行动 → 观察 → 再思考 → ...             │
│  例：问 "帮我查天气然后推荐穿什么"               │
│       → 调天气工具 → 分析结果 → 给出建议         │
└─────────────────────────────────────────────┘
```

**你现在在第二层**：LLM + Function Calling。阶段一就是搭建这个基础。

## 二、核心概念：LLM 的 Function Calling 是怎么工作的？

### 不是 LLM "调用"你的函数

这是最容易误解的地方。流程是这样的：

```
1. 你告诉 LLM："我有这些工具可用"（发送 tools 参数）
       ↓
2. LLM 分析用户问题，决定"我需要用工具 X"
       ↓
3. LLM 返回的不是文字，而是一个 JSON：
   {"name": "calculator", "arguments": {"expression": "123*456"}}
       ↓
4. 你的代码解析这个 JSON，实际执行 calculator("123*456")
       ↓
5. 把执行结果 "56088" 告诉 LLM
       ↓
6. LLM 基于结果生成最终回复："123×456 = 56088"
```

**LLM 不执行任何代码**，它只是输出一个"调用建议"。真正执行工具的是你的 Python 代码。

### 消息格式（OpenAI 协议）

LLM 对话用 messages 数组维护上下文，每条消息有 role：

```python
messages = [
    {"role": "system",    "content": "你是一个有用的助手"},   # 系统指令
    {"role": "user",      "content": "帮我算 123*456"},       # 用户输入
    {"role": "assistant", "content": None, "tool_calls": [...]}, # LLM 决定调工具
    {"role": "tool",      "content": "56088", "tool_call_id": "..."}, # 工具结果
    {"role": "assistant", "content": "123×456 = 56088"}       # LLM 最终回复
]
```

这就是你在 `llm_client.py` 里看到 `messages: list[dict]` 的含义。

## 三、代码详解

### 3.1 llm_client.py —— LLM 客户端

打开 `src/llm_client.py`，对照着看：

```python
class LLMClient:
    def __init__(self):
        # 从 .env 读配置 —— 为什么这么设计？
        # 因为 API Key 不能写死在代码里，也不能提交到 git
        self.api_key = os.getenv("DEEPSEEK_API_KEY")
        self.base_url = os.getenv("DEEPSEEK_BASE_URL")
        self.model = os.getenv("DEEPSEEK_MODEL", "deepseek-chat")
        self.client = OpenAI(api_key=self.api_key, base_url=self.base_url)
```

**关键知识点**：DeepSeek 的 API 是 OpenAI 兼容的，所以可以用 `openai` 这个包直接调。`base_url` 指向 DeepSeek 而非 OpenAI 的服务器。

```python
    def chat(self, messages, tools=None, ...):
        # 构建请求参数
        kwargs = {"model": self.model, "messages": messages, ...}
        if tools:
            kwargs["tools"] = tools    # 如果有工具定义，就传给 LLM

        response = self.client.chat.completions.create(**kwargs)
        # ↑ 这一行发出 HTTP 请求到 api.deepseek.com
```

**你不需要理解 OpenAI SDK 内部怎么发 HTTP 请求**，Java 里你用过 RestTemplate/HttpClient，原理一样——POST JSON 到服务器，拿回 JSON。

返回值的处理：
```python
return {
    "content": msg.content,        # 如果 LLM 直接回复，这里有文字
    "tool_calls": _parse_tool_calls(msg),  # 如果 LLM 想调工具，这里有调用信息
    "model": response.model,       # 实际用的模型（可能和请求的不一样）
    "usage": {...},                # token 消耗量
}
```

**一个响应里 content 和 tool_calls 互斥**：LLM 要么直接说话，要么说"我要调工具"。

#### 🤔 答疑：这行代码里的几个问号

上面这行核心调用拆开看，藏着好几个 Python 新手容易困惑的点：

```python
response = self.client.chat.completions.create(**kwargs)
```

**① `OpenAI()` 为什么不传 model？**

```python
self.client = OpenAI(api_key=self.api_key, base_url=self.base_url)
#                     ↑ 只有认证和地址，没有 model
```

`OpenAI()` 构造函数只负责「连到哪、怎么认证」，不负责「用什么模型」。model 是 HTTP 请求体的一个字段，每次调 `chat()` 时才通过 `kwargs["model"]` 传进去。类比 Java：`HttpClient` 构造时不传 URL，URL 在构建 `HttpRequest` 时才指定。

**② `.chat.completions.create()` 是什么链式调用？**

这对应 OpenAI REST API 的 URL 路径：

```
POST https://api.deepseek.com/v1/chat/completions
                          └──────┘  └──────────┘
                      client.chat  .completions.create()
```

SDK 内部把 URL 路径拆成对象层级。`create()` 是固定的方法名——OpenAI SDK 约定所有资源用 `create()` 做 POST 创建、`list()` 做 GET 列表。类比 Java 的 `RestTemplate.postForObject(url, body, ...)`。

**③ `**kwargs` 前面为什么有两个星号？**

这是 Python 的**字典解包**语法。对比：

```python
# ❌ 不加 ** —— 整个字典作为一个参数传进去
create(kwargs)   # create({"model": "...", "messages": ...})
# 函数只收到一个大 dict，不知道该怎么拆

# ✅ 加 ** —— 字典被"拆开"成多个独立参数
create(**kwargs)  # create(model="...", messages=[...], temperature=0.7)
# 函数收到三个命名参数，这才是它期望的
```

Java 里没有这个能力——你不能把一个 `Map` "拆开"成方法参数，只能一个一个手动传。

**④ `response` 变量名是 API 定义的？**

不是。它就是你自己起的普通变量名，叫 `result`、`resp`、`whatever` 都行。它之所以有意义，是因为 `.create()` 返回的对象上有 `.choices[0].message` 等属性，后续通过 `response.choices`、`response.model` 去读。

**⑤ 为什么不像 Java 那样声明类型？**

这是 Java 和 Python 最核心的差异：

```java
// Java：类型写在左边，编译时检查
ChatCompletion response = client.chat().completions().create(params);
```

```python
# Python：变量没有类型声明，类型由右边返回值决定
response = self.client.chat.completions.create(**kwargs)
```

Python 可以加类型注解（给 IDE 和人看的提示），但解释器完全忽略它：

```python
# 加上类型注解后，和 Java 的视觉感受就很接近了
from openai.types.chat import ChatCompletion

response: ChatCompletion = self.client.chat.completions.create(**kwargs)
```

**记住：Python 里变量没有类型，值才有类型。**

### 3.2 tools.py —— 工具注册与执行

#### 🤔 答疑：为什么 tools.py 没有 `class` 和 `__init__`？

观察两个文件的对比：

```python
# llm_client.py —— 有 __init__，因为需要记住状态
class LLMClient:
    def __init__(self):
        self.api_key = ...     # 状态：API 密钥
        self.client = ...      # 状态：HTTP 连接池
```

```python
# tools.py —— 没有 class，因为不需要记住状态
TOOL_REGISTRY = {}             # 模块级变量，不是实例属性

def calculator(expression):    # 纯函数：输入 → 输出，不依赖 self
def execute_tool(name, args):  # 从全局注册表取，不需要实例
```

判断要不要 `__init__` 的简单规则：

| 情况 | 用类 + `__init__` | 直接用模块级函数 |
|------|:---:|:---:|
| 需要保存连接、配置、缓存？ | ✅ | ❌ |
| 函数纯粹是输入→输出？ | ❌ | ✅ |
| 类比 Java | `@Service` + 构造器注入 | `static` 工具方法 |

`LLMClient` 要记住 `api_key` 和连接池 → **类**。`calculator()` 有参数就出结果 → **纯函数**。

### 3.3 llm_client 和 tools 是如何配合的？

关键理解：**这两个模块是互相独立的，不直接 import 对方**。它们在 `test_phase1.py`（以及未来的 Agent 循环）里被串联起来。

```
           test_phase1.py（调度者——相当于 Java 的 Controller）
          ┌───────────────────────────────────────────────┐
          │                                               │
          │  ① get_tool_definitions() ←── src/tools.py    │
          │     ↓ 拿到工具定义列表                          │
          │  ② client.chat(messages, tools=defs)           │
          │     ↓ 发给 LLM               ←── src/llm_client.py
          │  ③ LLM 返回 tool_calls                        │
          │     ↓ "我要调 calculator, 参数 123*456"         │
          │  ④ execute_tool(name, args)  ←── src/tools.py │
          │     ↓ 真正执行计算器                            │
          │  ⑤ 把结果塞回 messages，再次调 client.chat()    │
          │     ↓                                         │
          │  ⑥ LLM 返回最终答案                            │
          │                                               │
          └───────────────────────────────────────────────┘
```

目前的流程：

```python
# test_phase1.py 里的实际代码（简化）
client = LLMClient()                              # 来自 llm_client.py
tools = get_tool_definitions()                    # 来自 tools.py

response = client.chat(messages, tools=tools)     # LLM 决定调哪个工具

if response["tool_calls"]:                        # LLM 想调工具
    tc = response["tool_calls"][0]
    result = execute_tool(tc["name"], args)       # 来自 tools.py，真正执行
    # ← 这里还缺一步：把 result 塞回 messages 再调 LLM（阶段二实现）
```

**所以现阶段这两个文件其实还没有直接关联**——它们都是被外部"调度者"调用的独立模块。阶段二的 Agent 循环就是这个调度者，它会自动完成"调 LLM → 执行工具 → 结果反馈 → 再调 LLM"的闭环。

打开 `src/tools.py`，这里有几个重要设计模式：

#### 工具注册表（Registry Pattern）

```python
TOOL_REGISTRY: dict = {}  # 全局字典，相当于 Java 里的 Map<String, ToolMeta>

def register_tool(name, description, parameters, func):
    TOOL_REGISTRY[name] = {...}  # 往字典里存
```

这和 Java 的依赖注入/IoC 容器一个思路：用一个中心注册表管理所有可用工具，Agent 通过名字查找和执行。

#### 工具定义格式

```python
{
    "type": "function",      # OpenAI 固定格式
    "function": {
        "name": "calculator",
        "description": "执行数学计算",   # ← LLM 靠这个判断什么时候用
        "parameters": {                 # ← JSON Schema，告诉 LLM 参数格式
            "type": "object",
            "properties": {
                "expression": {"type": "string"}
            },
            "required": ["expression"]
        }
    }
}
```

这和 Java 里定义接口签名类似——你声明方法名、参数、返回值，调用方按约定调用。

#### 执行工具

```python
def execute_tool(name, arguments):
    func = TOOL_REGISTRY[name]["func"]   # 从注册表取函数
    result = func(**arguments)           # Python 的 ** 解包，相当于 func(expression="123*456")
    return str(result)                   # 强制转字符串
```

## 五、刻意踩坑 —— 为什么要这么写？

| 坑点 | 现象 | 学到什么 |
|------|------|---------|
| calculator 用 eval() 不校验参数 | 传 `"__import__('os').system('rm -rf /')"` 会直接执行 | 工具参数必须校验，eval 是安全隐患 |
| 工具描述模糊 | LLM 不知道该工具擅长什么，可能乱用 | 描述 = 工具的使用说明书，越清晰 LLM 用得越准 |
| search_knowledge 返回 dict | LLM 收到 `{'fastapi': '...'}` 不知道怎么办 | 工具返回值应该是 LLM 能直接理解的格式（通常是字符串） |
| search_knowledge 匹配太简陋 | 用户问 "FastAPI 是什么" 找不到 key "fastapi" | 搜索逻辑要考虑同义词、模糊匹配、自然语言 |

**这些坑不是 bug，是教材。** 面试时你说"我踩过这些坑并且修复了"，比说"我看过文档"有说服力 10 倍。

## 七、下一步（阶段二预告）

你现在有了：
- ✅ `llm_client.py` — 会发请求给 LLM
- ✅ `tools.py` — 有工具能干活

但你还**没有 Agent**——现在需要人手动把 LLM 返回的 tool_calls 拿去执行，再把结果塞回给 LLM。阶段二要做的就是：

```
while True:
    response = llm.chat(messages)
    if response 有 tool_calls:
        执行工具 → 结果塞回 messages
    else:
        输出最终答案 → break
```

这就是 **ReAct 循环**的核心：Think → Act → Observe → Think → ...
