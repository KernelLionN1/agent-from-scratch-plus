## 一、先理解：阶段二的 Agent 有什么问题？

阶段二的 `run()` 方法：

```python
def run(self, user_message):
    messages = [
        {"role": "system", "content": "..."},
        {"role": "user", "content": user_message},
    ]
    # ... 循环 ...
```

问题：**每次调用 run()，messages 都从头构建**。这意味着：

```
run("我叫小明")     → Agent 回答 → messages 销毁
run("我叫什么？")   → Agent 不知道 ← 因为上一轮的 messages 已经被丢弃了！
```

就像每次对话都换一个新的大脑。阶段三解决的就是这个问题。

---

## 二、核心概念：记忆系统

### 2.1 记忆的本质

记忆 = 把 messages 保存到一个**跨 run() 调用存活**的地方。

```python
# 阶段二：messages 是局部变量，函数返回就消失
def run(self, user_message):
    messages = [...]   # ← 新建，用完丢弃
    ...

# 阶段三：messages 存在 self.memory 里，跨调用保留
def run(self, user_message):
    self.memory.add_user(user_message)   # ← 追加到持久存储
    messages = self.memory.get_messages() # ← 取出（含历史）
    ...
```

### 2.2 为什么需要截断？

LLM 有**上下文窗口**限制（DeepSeek-chat ~64K tokens）。对话越长，messages 越大。当超过窗口时，API 直接报错。

截断策略就是：**在 messages 超过限制之前，主动裁剪掉最不重要的部分。**

```
完整历史：[system] [msg1] [msg2] [msg3] ... [msg50] [msg51] ← 51 条消息
                                                    ↑
                                    上下文窗口只能容纳 40 条
                                    ↓
截断后：  [system] [msg40] [msg41] ... [msg50] [msg51] ← 保留最近 + system
                ↑ 前面的被丢弃
```

## 三、代码详解

### 3.1 ConversationMemory —— 消息存储

```python
class ConversationMemory:
    def __init__(self, max_messages=20, max_tokens=4000):
        self._messages = []          # 内部列表存储所有消息
        self.max_messages = 20       # 滑动窗口大小
        self.max_tokens = 4000       # token 上限
```

对应 Java：

```java
    public List<Message> getMessages(String strategy) { ... }
}
```

### 3.2 三种截断策略

| 策略 | 行为 | 优点 | 缺点 |
|------|------|------|------|
| `none` | 不截断，返回全部 | 零丢失 | 超出窗口时直接报错 |
| `sliding_window` | 保留 system + 最近 N 条 | 实现简单 | 可能丢失重要的早期信息 |
| `token_limit` | 按 token 数截断 | 精确控制成本 | 估算不准（中文尤其严重） |

滑动窗口的实现：

```python
def get_messages(self, strategy="sliding_window"):
    system_msgs = [m for m in self._messages if m["role"] == "system"]
    other_msgs = [m for m in self._messages if m["role"] != "system"]
    recent = other_msgs[-self.max_messages:]    # 只取末尾 N 条
    return system_msgs + recent                 # system 始终保留
```

**关键设计点**：system 消息永不删除。因为 system prompt 定义了 LLM 的行为规则，丢了它 LLM 可能行为异常。

### 3.3 Token 估算 —— 刻意不准

```python
def _estimate_tokens(self, messages):
    total_chars = 0
    for msg in messages:
        total_chars += len(msg.get("content", "") or "")
    return total_chars // 4    # ← 极其粗糙！
```

为什么不准？

| 内容 | 实际 token 数 | 字符数/4 估算 | 误差 |
|------|:---:|:---:|:---:|
| `"Hello world"` | ~2 | 11/4=2 | 接近 |
| `"你好世界"` | ~4 | 4/4=1 | 严重低估 |
| `"print('hello')"` | ~5 | 15/4=3 | 低估 |

**面试问到时**：应该用 `tiktoken` 库精确计算，它知道每个模型的分词规则。

### 3.4 Agent 重构 —— 集成记忆

阶段二 → 阶段三的核心变化：

```python
# ── 阶段二：每次 run() 重建 messages ──
class ReActAgent:
    def run(self, user_message):
        messages = [{"role": "system", ...}, {"role": "user", ...}]  # 新建
        while True:
            response = self.llm.chat(messages=messages, ...)
            # ...

# ── 阶段三：messages 来自 memory ──
class ReActAgent:
    def __init__(self):
        self.memory = ConversationMemory()  # ← 记忆实例
        self.memory.set_system("...")       # ← system 存一次

    def run(self, user_message):
        self.memory.add_user(user_message)  # ← 追加用户消息
        while True:
            messages = self.memory.get_messages(strategy=...)  # ← 从记忆取
            response = self.llm.chat(messages=messages, ...)
            if response["content"]:
                self.memory.add_assistant(content=...)  # ← 回答也存
            if response["tool_calls"]:
                self.memory.add_assistant(tool_calls=...)  # ← 调用也存
                self.memory.add_tool_result(...)           # ← 结果也存
```

### 3.5 新增安全机制：max_iterations

```python
if iteration > self.max_iterations:
    return "抱歉，处理超时，请尝试简化问题后重试。"
```

这是阶段二「刻意踩坑」的修复——给 `while True` 加了个保险丝。面试时这就是一个很好的例子："我先故意不设限制观察问题，然后加上 max_iterations 作为保护。"
