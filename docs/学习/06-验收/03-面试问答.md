# 03-面试问答：15 道核心面试题 + 标准答案

> 覆盖 4 类：概念理解、架构设计、代码实践、生产经验

## 一、概念理解（4 题）

### Q1：什么是 ReAct Agent？跟普通 LLM 调用有什么区别？

> ReAct（Reasoning + Acting）是 LLM Agent 的核心范式：LLM 不只是回答问题，而是"思考 → 行动 → 观察 → 再思考"的循环。普通 LLM 调用：输入→输出，一次完成。ReAct Agent：输入→LLM思考→决定调工具→执行工具→观察结果→再思考→...→最终输出。本质是把 LLM 从"答题器"升级为"决策器"。

### Q2：Function Calling 的原理是什么？

> 在 API 请求中传入 tools 参数（函数定义 JSON Schema），LLM 返回时可能包含 tool_calls 字段（函数名+参数），而不是纯文本。调用方解析 tool_calls、执行对应函数、把结果作为 tool 消息追加到对话历史，继续调 LLM。LLM 根据工具结果决定下一步。

### Q3：LangGraph 的条件边和固定边有什么区别？

> 固定边（add_edge）：程序员编译时决定 A→B，每次执行都一样。条件边（add_conditional_edges）：运行时调路由函数，根据当前 State 决定走哪。我们的 should_continue() 根据 LLM 是否返回 tool_calls 决定走 tools 还是 END。这是 LLM 动态路由的核心机制。

### Q4：InMemory 和 SQLite 持久化的架构区别？

> InMemory 存在进程内存，进程重启丢失。SQLite 存在磁盘，重启可恢复。我们用策略模式设计：ConversationMemory 通过 history_backend 参数切换后端，SQLiteChatMessageHistory 实现了与 InMemoryChatMessageHistory 完全相同的接口（add_message/messages/clear），调用方无感切换。

## 二、架构设计（4 题）

### Q5：多 Agent 协作怎么设计？消息总线的作用是什么？

> 角色拆分（Planner/Coder/Reviewer）+ 消息总线 + 编排器。消息总线是 Agent 间的通信层：send() 发送、receive() 拉取（偏移量防重复）、broadcast() 广播。注意区分"peek vs poll"——receive() 应消费消息而非只读。parallel 执行用 asyncio.gather + to_thread 包装同步 LLM 调用。

### Q6：上下文压缩的两级策略怎么设计的？

> 轻量（10%触发，<1ms）：纯字符串操作——剔除失败工具调用、口语化改写、合并同类消息。重量（70%触发，~1s）：调 LLM 做摘要。两者都用增量锚点——只处理上次压缩之后的新消息，O(1) 固定开销。参考 Factory.ai 的生产实践。

### Q7：Prompt 三层组装的思路是什么？

> stable 层（缓存）：人格 + 工具指导 + 规则，对话中不变。context 层（可刷新）：用户偏好、项目信息，按需加载。volatile 层（动态）：时间戳 + 预算警告，每次重新生成。借鉴 Hermes Agent 的设计。

### Q8：高并发 text2sql 怎么设计？

> FastAPI + Redis 队列削峰 + Worker 消费 + SQLAlchemy 连接池 + 读写分离。入口限流（100/min），推入队列返回 task_id。Worker 异步消费：LLM 生成 SQL → 只读副本查询 → LLM 解释结果 → 缓存。相同问题走 Redis TTL 缓存，不重复调 LLM。

## 三、代码实践（4 题）

### Q9：Python asyncio.gather 有什么坑？

> ① 忘加 await → 协程创建后丢弃。② 同步 LLM 调用需 asyncio.to_thread 包装。③ 不加 return_exceptions=True → 一个失败全挂。④ asyncio.wait_for 超时 → 丢弃已完成的部分结果。解决：return_exceptions=True + 先收集再超时检查。

### Q10：为什么要用 `Annotated[list, add]` 而不是普通 list？

> LangGraph 的 reducer 机制。普通 list 每次节点更新会覆盖旧值。Annotated[list, add] 使用 operator.add 做 reducer，新值追加到旧值后面。我们的 AgentState 里 messages 和 tool_results 都用这个，保证多轮工具调用结果不丢失。

### Q11：你是怎么处理 LLM 调用失败的？

> 三层防护：① LangChain 内置 max_retries=3（指数退避）；② Day3 手写的重试+熔断；③ Hermes Agent 参考的 fallback provider 链（换模型继续）。Day6 的 CallbackManager 把错误事件桥接到 logging。

### Q12：怎么保证多租户数据隔离？

> 智能园区场景需要 4 层：campus_id → tenant_id → user_id → conversation_id。每个 ID 冗余到消息表，WHERE 条件一次过滤。SessionManager 维护活跃会话，get_history() 默认只取当前会话。简单 SaaS 场景 3 层（tenant+user+conversation）即可。

## 四、生产经验（3 题）

### Q13：从 Demo 到生产还差什么组件？

> Nginx 负载均衡、Redis 消息队列削峰、SQLAlchemy 连接池、slowapi 限流、pybreaker 熔断、Prometheus 监控、ELK 日志。Agent 实例池（工厂模式已有雏形），Worker 水平扩展。

### Q14：LangChain 的流式输出怎么实现？

> LLMClient.astream() 使用 LangChain 的 astream_events() 逐 token 产出。Agent 层用手动循环替代 LangGraph 的 invoke()，每次 LLM 调用流式输出，工具执行间插入 progress 事件（thinking → token → tool_start → tool_result → done）。

### Q15：TypeScript Agent 框架和 Python 的定位有什么区别？

> Python 主导 Agent 编排层（多 Agent 协作、RAG、复杂推理），TypeScript 主导前端嵌入层（Vercel AI SDK 20K+ stars、Mastra 8K+）。两者不是替代关系，是分层协作。Java 在业务中台层做流程编排，通过 HTTP 调用 Python AI 中台。未来 3-5 年 Python 仍是 Agent 编排的主战场。
