## 二、增量压缩（Factory.ai 方案）

### 2.1 问题

Day5 的 `compress_heavy()` 每次都把全部消息传给 LLM：

```
第1次压缩: 100条消息 → LLM → 摘要
第2次压缩: 150条消息 → LLM → 新摘要（包含前100条的内容，重复计算）
第3次压缩: 200条消息 → LLM → 新摘要（越来越贵）
```

每次都是 O(n) 重复压缩已压缩过的内容。

### 2.2 解决方案：增量锚点

```
10% → compress_light() → 处理消息 0-N, 锚点=N
20% → compress_light() → 只处理消息 N-2N（增量），锚点=2N
30% → compress_light() → 只处理消息 2N-3N（增量），锚点=3N
```

每次只处理上次之后新增的消息，O(1) 固定开销。同样适用于轻量和重量压缩。

### 2.3 实现

```python
class ConversationMemory:
    _anchor_summary: str = ""      # 累积摘要
    _anchor_msg_count: int = 0     # 压缩到第几条了

    def compress_heavy(self, messages, llm):
        # 只取锚点之后的新消息
        new_msgs = messages[self._anchor_msg_count:]

        if self._anchor_summary:
            prompt = f"已有摘要: {self._anchor_summary}\n新增: {new_msgs}\n合并输出:"
        else:
            prompt = f"压缩: {new_msgs}"

        summary = llm.chat(prompt)
        self._anchor_summary = summary       # 更新锚点
        self._anchor_msg_count = len(messages)
        return [system_msgs, {"role": "user", "content": f"[摘要] {summary}"}]
```

### 2.4 对比

| | Day5（全量） | Day6（增量） |
|---|---|---|
| 第 N 次压缩的输入 | 全部 N 条消息 | 锚点之后的新消息 |
| LLM 调用开销 | O(n) 递增 | O(1) 固定 |
| 首次调用 | 全量 | 全量（一样） |
| 消息独立性 | 无状态 | 有状态（锚点需管理） |

## 三、流式输出

### 3.1 LLM 层面

LangChain 的 `astream_events()` 逐 token 产出：

```python
async for event in llm.astream_events(messages, version="v2"):
    if event["event"] == "on_chat_model_stream":
        token = event["data"]["chunk"].content
        yield {"type": "token", "content": token}   # 逐字输出
```

这跟 Java SSE（Server-Sent Events）一个道理——不等人说完，说一个字发一个字。

### 3.2 Agent 层面

用手动循环替代 LangGraph 的 `invoke()`，每步流式输出：

```python
async for event in agent.astream("计算 100+200"):
    # event: {"type": "thinking"} → {"type": "token"} → {"type": "tool_start"} → ...
```

事件序列：
```
thinking(step=0) → token("100") → token("+") → token("200")
→ tool_start("calculator") → tool_result("300")
→ thinking(step=1) → token("结果") → token("是") → token("300") → done
```

## 四、MEMORY.md 跨会话记忆

### 4.1 与 SQLite 的区别

```
SQLiteChatMessageHistory  → 会话内消息（切换会话就看不到了）
FileMemoryStore           → 跨会话记忆（换了项目、换了时间都能读）

例子:
  用户: "我叫小明"
  → SQLite: 存在当前会话里
  → MEMORY.md: 写入 `- 用户名: 小明`
  下次用户开新会话 → Agent 从 MEMORY.md 读到 "用户名: 小明"
```

### 4.2 格式

```markdown
# MEMORY.md — Agent 持久化记忆
# 此文件跨会话保留，Agent 每次启动时自动加载

- 用户偏好: 喜欢简短回答
- 项目: agent-from-scratch-plus
- 用户名: 小明
```

简单可读，等价于 Java 的 Properties 文件。

### 4.3 使用

```python
from src.memory import FileMemoryStore

store = FileMemoryStore()
store.save("用户偏好", "喜欢简短回答")
mem = store.load()              # → "## 用户记忆\n- 用户偏好: 喜欢简短回答"
# 注入到 PromptBuilder 的 context 层
pb.load_context(mem)
```

## 五、回调机制

### 5.1 为什么不用 print()

```
print() 的问题:
  - 无法关闭（生产环境不想打日志到 stdout）
  - 无法重定向（测试时想收集到列表）
  - 无法扩展（想同时发到日志文件 + Slack 通知）
```

### 5.2 CallbackManager

```python
from src.callbacks import CallbackManager, get_callback_manager

cm = CallbackManager()

# 注册
cm.on("tool_executing", lambda name, args: logger.info(f"Tool: {name}"))
cm.on("error", lambda msg: slack.send(msg))

# 一键注册到 Python logging
import logging
cm.wrap(logging.getLogger("agent"))

# Agent 代码中
cm.emit("tool_executing", name="calc", args={"expr": "1+1"})
```

8 种事件：`agent_thinking` / `tool_executing` / `tool_result` / `compress_light` / `compress_heavy` / `llm_call_start` / `llm_call_end` / `error` / `memory_saved`

### 5.3 Java 对照

```java
// Spring Event
@EventListener
public void onToolExecuting(ToolExecutingEvent event) { ... }

// Guava EventBus
eventBus.register(listener);
eventBus.post(new ToolExecutingEvent("calc", args));
```

## 六、面试准备

**Q：增量压缩和全量压缩的区别？**
> 全量每次传全部消息给 LLM，O(n) 递增。增量只传上次压缩后新增的消息，O(1) 固定。但需要维护锚点状态（已压缩到第几条）。Factory.ai 的生产实践证明了增量方案在长对话中显著降低成本。

**Q：Streaming 怎么实现的？**
> LangChain 的 `astream_events()` 逐 token 产出。Agent 层用手动循环替代 LangGraph 的 invoke()，每步流式调 LLM，工具执行间插入 progress 事件。

**Q：MEMORY.md 和 SQLite 的区别？**
> SQLite 存会话内消息（会议话切换隔离），MEMORY.md 存跨会话记忆（用户偏好、项目信息）。一个管短期，一个管长期。

**Q：回调机制解决了什么？**
> 替代 print()，支持可插拔的日志/通知。同一事件可注册多个处理器（logging + Slack + 监控），关闭/移除不影响主流程。

**Q：`cm.on()` / `cm.emit()` / `cm.off()` 分别干什么？**
>
> 标准的发布-订阅模式：
> - `cm.on("事件名", handler)` — 订阅，说"当X发生时，执行这个函数"。同一事件可注册多个处理器。
> - `cm.emit("事件名", **data)` — 发布，说"X发生了，这里是数据"。所有注册的处理器依次调用。
> - `cm.off("事件名")` — 取消订阅，清空该事件的所有处理器。
>
> Java 对照：`on` ≈ `@EventListener` / `register()`，`emit` ≈ `publishEvent()` / `post()`，`off` ≈ `unregister()`。
>
> `wrap(logger)` 是便捷方法，内部帮你把 6 个 `cm.on(...)` 全写好了，一行代码接入 Python logging。

**Q：`logger.setLevel(logging.DEBUG)` 是干什么的？**
>
> Python logging 有级别过滤：`DEBUG < INFO < WARNING < ERROR < CRITICAL`。默认是 WARNING——只输出 WARNING 及以上。`wrap()` 注册的 handler 用了 INFO 和 DEBUG 两级（详细事件用 DEBUG）。不设 DEBUG 的话 DEBUG 级的日志会被吞掉。生产环境用 INFO，测试用 DEBUG 验证所有事件都注册了。
