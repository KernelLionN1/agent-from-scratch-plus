## 一、先理解：为什么需要全局状态？

阶段二的串行编排里，Orchestrator 自己能追踪所有步骤：

```
步骤1: plan = planner.execute()    ← 结果在 plan 变量里
步骤2: code = coder.execute()      ← 结果在 code 变量里
步骤3: review = reviewer.execute() ← 结果在 review 变量里
```

但问题来了：

1. **外部想知道进度**：一个长时间运行的编排任务，外部怎么知道当前到第几步了？
2. **Agent 之间共享数据**：Planner 的输出 Coder 要知道，Reviewer 的意见 Coder 也要知道
3. **并发安全**：阶段三的并行模式下，多个 Coder 同时读写同一个变量会怎么办？

全局状态就是解决这三个问题的——一个所有 Agent 都能读写的、线程安全的共享存储。

## 二、核心概念：SharedState

### 2.1 设计

```
SharedState
├── _data: dict            ← 实际存储（private，外部不能直接碰）
├── _version: int          ← 全局版本号（每次写入 +1）
├── _lock: threading.Lock  ← 互斥锁（保证线程安全）
├── set(key, value)  → int          ← 写入，返回新版本号
├── get(key, default) → Any         ← 读取（深拷贝，防止污染）
├── update(key, val, expected_v) → bool  ← 乐观锁更新
├── bypass_lock(key, val) → None    ← 【踩坑】绕过一切保护
├── init_progress(n) → int          ← 初始化任务进度
├── mark_task_done(agent, id, summary) → bool  ← 标记完成
└── snapshot() → dict               ← 完整快照
```

**Java 类比：**
```
SharedState ≈ ConcurrentHashMap<String, Object> + 手动 @Version 乐观锁
            ≈ JPA Entity 的 @Version 字段，但用于任意 KV 数据
```

### 2.2 为什么不用 Python 的全局变量？

```python
# ❌ 最原始的做法 —— 全局 dict
global_state = {}

# agent_a.py
global_state["progress"] = "done"  # Agent A 写入

# agent_b.py
global_state["progress"] = "working"  # Agent B 同时写入，覆盖了 A 的

# 问题：
# 1. 没有锁 → 并发写入会互相覆盖
# 2. 没有版本号 → 无法检测冲突
# 3. 引用直接暴露 → Agent 拿到 dict 后可以偷偷改
```

SharedState 把这些全局 dict 的坑全部封装了起来。

## 三、三大保护机制

### 3.1 互斥锁（`threading.Lock`）

```python
class SharedState:
    def set(self, key, value):
        with self._lock:              # ← 同一时刻只有一个线程能进入
            self._data[key] = deepcopy(value)
            self._version += 1
            return self._version

    def get(self, key, default=None):
        with self._lock:              # ← 读也要加锁！
            val = self._data.get(key, default)
            return deepcopy(val)      # ← 返回深拷贝
```

**为什么读也要加锁？**

```python
# 线程 A 正在写 _data["key"] = huge_object
# 线程 B 正在读 _data["key"]
# 如果读不加锁 → B 可能读到写到一半的数据（破数据）
# Python GIL 能保护单个 dict 操作，但不能保护复合操作
```

**为什么用 `threading.Lock` 而不 `asyncio.Lock`？**

因为我们的 LLM 调用是同步的（`requests` 库），用的是 `asyncio.to_thread` 线程池。Agent 的代码跑在线程里，不是协程里。所以用线程锁就够了。

### 3.2 乐观锁（版本号）

```python
# Agent A 读取状态
v_a = state.get_version()       # v_a = 5
data_a = state.get("counter")   # data_a = 0

# Agent B 抢先更新了
state.set("counter", 999)       # _version 变成 6

# Agent A 尝试更新 —— 版本号不匹配！
ok = state.update("counter", 42, expected_version=v_a)
# ok = False！因为 v_a(5) ≠ 当前 _version(6)
```

**流程图：**

```
时间 →

Agent A: 读(版本5) ──────────────── 想写(版本5) → 拒绝！
                                           
Agent B: ──── 读(版本5) ──── 写(版本6) ────

结果：B 的写入成功，A 的写入被拒绝。
      A 需要重新读最新状态，再试一次（重试逻辑留 Day3）。
```

**Java 类比：JPA 乐观锁**

```java
@Entity
public class Task {
    @Version
    private Long version;   // ← 这个字段就是我们的 _version
    
    private String status;
}

// 更新时 JPA 自动检查版本号
// UPDATE task SET status = 'done', version = 6 WHERE id = 1 AND version = 5
// 如果 affected rows = 0 → 版本冲突 → OptimisticLockException
```

### 3.3 深拷贝隔离

```python
# 写入一个列表
state.set("items", [1, 2, 3])

# 取出后外部修改
items = state.get("items")
items.append(999)    # ← 改了取出来的

# 内部不受影响
print(state.get("items"))  # [1, 2, 3]  ← 还是原来的！
```

Python 的 `=` 是引用传递。如果不用 `deepcopy`：

```python
# ❌ 不用深拷贝的后果
class BadState:
    def get(self, key):
        return self._data[key]  # ← 返回引用！

data = bad_state.get("items")
data.append(999)            # ← 改了内部数据！
# 没有锁、没有版本号、没有隔离 —— 三重灾难
```

## 四、代码走读

### 4.1 SharedState 核心方法

```python
class SharedState:
    def __init__(self):
        self._data = {}           # 核心存储
        self._version = 0         # 全局版本号
        self._lock = threading.Lock()  # 互斥锁

    def set(self, key, value) -> int:
        """写入值，返回新版本号（供后续乐观锁使用）"""
        with self._lock:
            self._data[key] = deepcopy(value)  # 深拷贝存储
            self._version += 1                  # 版本递增
            return self._version                # 返回新版本

    def get(self, key, default=None):
        """读取值，返回深拷贝（外部修改不污染内部）"""
        with self._lock:
            val = self._data.get(key, default)
            return deepcopy(val) if val is not None else default

    def update(self, key, value, expected_version) -> bool:
        """
        乐观锁更新：
        - 版本号匹配 → 写入，返回 True
        - 版本号不匹配 → 拒绝，返回 False
        """
        with self._lock:
            if self._version != expected_version:
                return False              # 冲突！
            self._data[key] = deepcopy(value)
            self._version += 1
            return True                  # 成功
```

### 4.2 进度追踪便利方法

```python
def init_progress(self, total_tasks):
    """初始化：总共有 N 个任务要完成"""
    return self.set("progress", {
        "phase": "planning",
        "total": total_tasks,
        "completed": 0,
        "results": {},
        "errors": [],
    })

def mark_task_done(self, agent_name, task_id, result_summary):
    """标记一个任务完成，记录是谁完成的、结果是什么"""
    with self._lock:
        progress = self._data.get("progress")
        progress["completed"] += 1
        progress["results"][f"{agent_name}_task{task_id}"] = {
            "summary": result_summary[:200],
        }
        self._version += 1
        return True
```

**注意：** `mark_task_done` 直接操作了 `_data["progress"]` 这个 dict。因为是在 `with self._lock` 内部，所以安全。但如果外部拿到 `progress` 引用后直接改，就不安全了——这就是 `bypass_lock` 要演示的踩坑场景。

### 4.3 Orchestrator 集成

```python
class Orchestrator:
    def __init__(self, bus, with_shared_state=False):
        ...
        if with_shared_state:
            self.shared_state = SharedState()
            # 注入到所有 Agent
            for agent in [self.planner, self.coder, self.reviewer]:
                agent.shared_state = self.shared_state

    def run_serial_with_state(self, requirement):

        self.shared_state.set("plan", plan)  # 保存中间结果
        
        # 后续步骤同理...
```

### 4.4 并行场景的状态追踪

```python
def run_parallel_with_state(self, requirement, n_coders=2):
    self.shared_state.init_progress(3)  # planner / coders / reviewer
    self.shared_state.set("phase", "planning")
    
    # Planner 完成
    plan = self.planner.execute(requirement)
    self.shared_state.mark_task_done("planner", 1, f"规划完成")
    self.shared_state.set("phase", "coding")
    
    # 并行 Coder —— 注意：每个 Coder 都注入了 shared_state
    coders = [CoderAgent(bus, f"coder-{i+1}") for i in range(n)]
    for c in coders:
        c.shared_state = self.shared_state  # ← 并行实例也要注入！
    
    # 并行执行
    codes = asyncio.run(asyncio.gather(...))
    
    # 记录每个 Coder 的结果
    for c in codes:
        self.shared_state.set(f"code_task{c['task_id']}", c["code"][:500])
    self.shared_state.mark_task_done("coders", 0, f"{len(codes)} 个 Coder 完成")
```

**关键细节：** 并行创建的 Coder 实例也需要注入 `shared_state`，因为它们是在 `run_parallel_with_state()` 内部动态创建的，不是 `__init__` 里的那三个。

## 五、【刻意踩坑】详解

### 5.1 bypass_lock —— 绕过一切保护

```python
def bypass_lock(self, key, value):
    """【踩坑】直接赋值，不加锁，不递增版本号"""
    self._data[key] = value
    #              ↑
    #   不深拷贝，不递增 _version
    #   这模拟了 Agent 拿到 _data 引用后直接 dict[key] = value
```

**演示效果：**

```
正常 set: 版本 5 → 6
bypass_lock 后: 版本 6 → 6（没变！）
用旧版本号 5 做 update → 成功（因为版本号没变，乐观锁检测不到修改！）
```

**真实对应：**

```python
# Agent 拿到了 shared_state 的 _data 引用（不应该，但可能发生）
data_ref = state._data  # ← Python 没有真正的 private
data_ref["key"] = "偷偷改的"  # ← 绕过了所有保护
```

### 5.2 版本冲突无自动重试

```python
ok = state.update("counter", 42, expected_version=old_version)
if not ok:
    # 【踩坑】当前：什么都不做，返回 False
    # Day3 应该：重新读 → 基于新值重新计算 → 再试
    
    # Day3 的正确做法（伪代码）：
    # for retry in range(3):
    #     new_val = state.get("counter")
    #     new_val += 1
    #     if state.update("counter", new_val, state.get_version()):
    #         break
```

### 5.3 全局 dict 的并发灾难

验证 8 里演示的场景：

```python
global_data = {"counter": 0}

# Agent A: 读(0) → sleep 0.2s → 写(0+1)
# Agent B: 读(0) → sleep 0.05s → 写(0+1)   ← B 更快
# 结果: counter = 1（不是 2！）
# 两个 Agent 都读了 0，都写了 1
# A 的写入覆盖了 B 的写入 —— 丢失了一次计数
```

**Java 类比：** 两个线程同时 `i++`，不加锁或 AtomicInteger 就会丢更新。

## 六、Java 开发者对照表

| Python 概念 | Java 等价 | 说明 |
|------------|----------|------|
| `SharedState` | `ConcurrentHashMap<String, Object>` + 手动版本控制 | 线程安全 KV 存储 |
| `threading.Lock` | `ReentrantLock` / `synchronized` | 互斥锁 |
| `with self._lock:` | `lock.lock(); try {...} finally {lock.unlock();}` | 自动获取/释放 |
| `update(key, val, v)` | JPA `@Version` + `OptimisticLockException` | 乐观锁 |
| `_version` 字段 | `@Version private Long version;` | 版本号 |
| `deepcopy(value)` | 手动 `clone()` 或序列化/反序列化 | 深拷贝隔离 |
| `bypass_lock()` | 直接 `map.put(key, val)` 不加锁 | 裸操作，没保护 |
| `_` 前缀 | `private` 字段 | 约定私有，不强制 |
| `snapshot()` | `new HashMap<>(map)` 浅拷贝 / 深拷贝 | 返回副本 |

### 实验 2：对比有锁 vs 无锁的并发表现

```python
import threading
import time
from src.shared_state import SharedState

# ── 无锁版本（裸 dict）──
raw_dict = {"sum": 0}

def add_to_raw(n):
    for _ in range(100):
        raw_dict["sum"] = raw_dict["sum"] + n
        time.sleep(0.001)

threads = [threading.Thread(target=add_to_raw, args=(1,)) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(f"裸 dict 结果: {raw_dict['sum']}  (期望 1000)")

# ── SharedState 版本 ──
state = SharedState()
state.set("sum", 0)

def add_to_state(n):
    for _ in range(100):
        v = state.get_version()
        cur = state.get("sum")
        ok = state.update("sum", cur + n, expected_version=v)
        if not ok:
            pass  # 【踩坑】冲突了也不重试！Day3 需要加
        time.sleep(0.001)

threads = [threading.Thread(target=add_to_state, args=(1,)) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()
print(f"SharedState 结果: {state.get('sum')}  (可能 < 1000，因为有冲突被丢弃)")
```

## 八、阶段四小结

| 学到了什么 | 对应知识点 |
|-----------|----------|
| 多 Agent 为什么需要共享状态 | 进度追踪、中间结果共享、外部可观测 |
| 三大保护机制 | Lock（互斥）、Version（乐观锁）、deepcopy（隔离） |
| 乐观锁 vs 悲观锁 | 乐观锁 = 先改再检查冲突；悲观锁 = 先锁再改 |
| bypass_lock 绕过保护 | Python 没有真正 private，_data 可以被外部拿到 |
| 无锁并发的覆盖问题 | 读-改-写三步不加锁 = 丢更新 |
| 版本冲突需要重试 | 当前只检测不重试，Day3 补全 |
| `threading.Lock` vs `asyncio.Lock` | 线程锁用于同步代码，协程锁用于异步代码 |
| deepcopy 隔离 | 返回副本而不是引用，防止外部偷偷修改 |
