## 一、先理解：为什么要并行？

阶段二的串行编排流程是这样的：

```
Planner ──10s──→ Coder ──15s──→ Reviewer ──12s──→ Coder(修复) ──8s──→ 结果
                                                            总耗时: ~45s
```

如果需求拆出了 3 个独立的子任务（比如「写冒泡排序」「写二分查找」「写快速排序」），
串行就得让一个 Coder 干活三次：

```
Planner → Coder(task1) → Coder(task2) → Coder(task3) → Reviewer → 结果
           15s            15s            15s
                         coder 总耗时: 45s
```

但这三个子任务是**互相独立的**——写冒泡排序不需要等二分查找写完。
并行就是让多个 Coder 同时开工：

```
            ┌─ Coder1(task1) 15s ─┐
Planner ────┼─ Coder2(task2) 15s ─┼──→ Reviewer → 结果
            └─ Coder3(task3) 15s ─┘
            coder 总耗时: 15s（不是 45s！）
```

## 二、核心概念：asyncio 异步模型

### 2.1 三种执行模式对比

```
串行（同步）
══════════════════════════════════════
task1() ────等待────→ task2() ────等待────→ task3()
总耗时 = t1 + t2 + t3


并行（多线程）
══════════════════════════════════════
Thread1: task1() ────等待────→
Thread2: task2() ────等待────→
Thread3: task3() ────等待────→
总耗时 = max(t1, t2, t3)
缺点：每个线程都要占用内存（~8MB/线程）


并行（asyncio 协程）
══════════════════════════════════════
Event Loop (单线程):
  await task1() ──→ 挂起，让出 CPU
  await task2() ──→ 挂起，让出 CPU
  await task3() ──→ 挂起，让出 CPU
  当 task1 完成 → 恢复 task1
  当 task3 完成 → 恢复 task3
  当 task2 完成 → 恢复 task2
总耗时 = max(t1, t2, t3)
优点：单线程，零线程开销
```

**Java 类比：**
- 串行 = 同步调用 `service1.process()`
- 多线程 = `CompletableFuture.supplyAsync(() -> task1(), executor)`
- asyncio = 类似 Java 21 虚拟线程 / Project Loom，但语法更简洁

### 2.2 async/await 核心规则

```python
# 定义协程函数：加 async
async def _coder_async(self, coder, subtask, task_id):
    ...

# 调用协程 = 创建协程对象（不执行！）
coro = _coder_async(coder, subtask, 1)      # ← 只是创建，没开始跑

# await = 挂起当前协程，等结果
result = await coro                           # ← 真正执行并等待

# asyncio.gather = 同时启动多个协程，等全部完成
results = await asyncio.gather(coro1, coro2, coro3)  # ← 并行跑

# asyncio.run = 在同步代码里启动事件循环
results = asyncio.run(main_coroutine())       # ← 桥接 async → sync
```

### 2.3 为什么 async 函数调用不立即执行？

**这是 Python async 和普通函数最本质的区别。**

```
普通函数调用：
═══════════════════════════════════════
def add(a, b):
    return a + b

result = add(1, 2)    # ← 立即执行，返回 3
                        # 控制流进入 add() → 执行 return a+b → 出来
                        # result = 3


async 函数调用：
═══════════════════════════════════════
async def _coder_async(self, coder, subtask, task_id):
    code = await asyncio.to_thread(coder.execute, subtask)
    return {"task_id": task_id, "code": code}

coro = _coder_async(coder, subtask, 1)   # ← 不执行！返回协程对象
                                           # 控制流根本没进函数体
                                           # 只是一个「待执行的计划」
```

调用 async 函数相当于**下订单**，而不是**上菜**：

```python
coro = _coder_async(coder, subtask, 1)
#       ↑
#   "我预定了一份异步任务，但现在不做"
#   返回的是一个 Coroutine 对象（相当于一张订单小票）

result = await coro
#         ↑
#   "现在开始执行这份订单，等它完成"
#   控制流进入 _coder_async 函数体，真正调用 LLM
```

**Java 类比：** Java 里创建 Future 也不等于立即执行，必须提交给 Executor：

```java
// 创建 Callable —— 不会执行
Callable<String> task = () -> coder.execute(subtask);

// 提交给 Executor —— 才开始执行
Future<String> future = executor.submit(task);
```

### 2.4 协程数量需要提前声明吗？

**不需要。** 协程对象是动态创建的，有多少个子任务就创建多少个。

```python
# orchestrator.py 实际代码 —— 动态生成
tasks = [
    self._coder_async(coders[i], subtasks[i], i + 1)
    for i in range(len(subtasks))   # ← Planner 拆出几个就是几个
]
return await asyncio.gather(*tasks)
#                          ↑
#            *tasks 解包：动态适配任意数量
```

流程示意：

```
subtasks = ["子1", "子2", "子3"]        → 列表推导式自动生成 3 个协程
subtasks = ["子1", "子2", "子3", "子4", "子5"]  → 自动生成 5 个协程

gather(*tasks) 不关心数量，来多少吃多少
```

### 2.5 Python 协程 vs Go goroutine

**目标一样——"让单线程同时处理多个等待 IO 的任务"。但机制完全不同。**

| | Python asyncio | Go goroutine |
|------|-------------|------------|
| 关键词 | `async` / `await` | `go` |
| 切换方式 | **显式** — 必须写 `await` 标记切换点 | **隐式** — 运行时自动检测阻塞并切走 |
| 忘了标记的后果 | 阻塞整个线程，其他协程卡死 | 不存在这个问题 |
| 调度器 | 事件循环（单线程） | Go 运行时（多线程） |

同一个场景对比：

```python
# Python: 必须用 await 明确告诉运行时 "这里可以切走"
async def fetch(url):
    resp = await aiohttp.get(url)   # ← await 不能忘
    return resp.text

results = await asyncio.gather(fetch("A"), fetch("B"), fetch("C"))
```

```go
// Go: 看起来是同步的，运行时自动切换
func fetch(url string) string {
    resp, _ := http.Get(url)   // ← 看起来同步，运行时在 IO 阻塞时自动切走
    return resp
}

go fetch("A")   // ← go 关键字开 goroutine
go fetch("B")
go fetch("C")
```

**对我们项目的意义：** 你写的 `_coder_async` 之所以必须手动 `await asyncio.to_thread(...)`，就是因为 openai SDK 是同步的。Day4 用 LangChain 的 `ainvoke()` 也依然要写 `await`——Python 的异步是传染的，"调用 async 函数的地方也必须是 async"。

## 三、代码走读：run_parallel() 完整链路

### 3.1 入口

```python
def run_parallel(self, requirement: str, n_coders: int = 2, timeout: float = 120) -> dict:
```

这是一个**同步方法**（没有 `async def`），内部用 `asyncio.run()` 桥接到异步世界。

### 3.2 步骤拆解

```
run_parallel("实现冒泡排序和二分查找", n_coders=2)

步骤1: plan = self.planner.execute(requirement)
       │ 同步调 LLM，得到规划文本
       └─ plan = "### 子任务1: ... \n### 子任务2: ..."

步骤2: subtasks = self._parse_subtasks(plan)
       │ 正则拆分规划文本为子任务列表
       └─ subtasks = ["子任务1内容", "子任务2内容"]

步骤3: coders = [CoderAgent(bus, f"coder-{i+1}") for i in range(2)]
       │ 为每个子任务创建独立的 Coder 实例
       │ 为什么要独立？→ 共享 LLMClient 会导致 HTTP 请求串行化
       └─ coders = [CoderAgent(..., "coder-1"), CoderAgent(..., "coder-2")]

步骤4: codes = asyncio.run(_run_all())
       │ 启动事件循环，执行内部协程
       │
       └─ async def _run_all():
              tasks = [
                  self._coder_async(coders[0], subtasks[0], 1),
                  self._coder_async(coders[1], subtasks[1], 2),
              ]
              return await asyncio.gather(*tasks)
              │
              │  gather 同时调度两个协程:
              │
              ├─ _coder_async(coders[0], ...)
              │   └─ await asyncio.to_thread(coders[0].execute, subtasks[0])
              │       └─ 线程池里: execute() → call_llm() → POST DeepSeek API
              │          → 阻塞等待 HTTP 响应 → 返回代码字符串
              │
              └─ _coder_async(coders[1], ...)    ← 与上面并行
                  └─ await asyncio.to_thread(coders[1].execute, subtasks[1])
                      └─ 线程池里: execute() → call_llm() → POST DeepSeek API
                         → 阻塞等待 HTTP 响应 → 返回代码字符串

步骤5: combined = "\n\n".join(每份代码拼接)

步骤6: review = self.reviewer.execute(combined)
       │ 审核汇总后的代码
       └─ 最终返回 {plan, codes, combined, review, timing}
```

### 3.3 _coder_async 做了什么

```python
async def _coder_async(self, coder: CoderAgent, subtask: str, task_id: int) -> dict:
    # asyncio.to_thread: 把同步调用丢进线程池，不阻塞事件循环
    # 相当于 Java 的 CompletableFuture.supplyAsync()
    code = await asyncio.to_thread(coder.execute, subtask)
    #                    ↑
    #   关键：这里不是直接 await coder.execute(subtask)
    #   因为 execute() 是同步方法（内部用 requests 库做 HTTP 调用）
    #   直接 await 会阻塞整个事件循环，其他协程全部卡住
    #   to_thread 把阻塞操作丢到线程池，事件循环可以继续处理其他协程
    return {"task_id": task_id, "subtask": subtask, "code": code}
```

### 3.4 为什么每个 Coder 要独立实例

```python
coders = [CoderAgent(self.bus, f"coder-{i+1}") for i in range(n)]

# CoderAgent.__init__ 里:
#   self.llm = LLMClient()    ← 每个 Coder 有自己的 LLM 客户端！
```

如果所有 Coder 共享一个 CoderAgent 实例：

```python
# ❌ 错误做法
only_coder = CoderAgent(bus, "coder-1")
tasks = [
    _coder_async(only_coder, subtasks[0], 1),
    _coder_async(only_coder, subtasks[1], 2),  # ← 同一个 coder！
]
# 虽然 asyncio.to_thread 会在不同线程执行，
# 但 only_coder.execute() 调的是同一个 LLMClient.chat()
# OpenAI SDK 内部有连接池，可能串行化请求
```

### 3.5 下划线 `_` 前缀的含义

`_coder_async`、`_parse_subtasks`、`_run_all` 这些方法名前面的下划线是 Python 约定：

```python
class Orchestrator:
    def run_parallel(self, ...):       # 公开 API —— 外部调用
        ...

    async def _coder_async(self, ...): # 内部方法 —— "外部别用"
        ...
    def _parse_subtasks(self, ...):    # 内部方法 —— "外部别用"
        ...
```

它不是强制的（不像 Java 的 `private`），只是约定。你依然能 `orch._coder_async(...)`，但 IDE 和 lint 工具会提示"这是私有方法"。

**Java 类比：**

| Python | Java | 强制？ |
|--------|------|-------|
| `_method` | `private` 或 package-private | Python 不强制，Java 编译期强制 |
| `__method` | `private` + name mangling | Python 名字会被改写为 `_Class__method` |
| `method_` | 无（避免和关键字冲突） | 如 `type_` 避免和 `type` 冲突 |

Python 没有真正的 `private`，靠 `_` 做社会契约。

## 四、asyncio.to_thread 为什么是「伪异步」

### 4.1 原理

```
真正的异步（如 httpx.AsyncClient）
═══════════════════════════════════════
await client.post(url)    ← 不占线程！
  事件循环: "你去发请求，发完叫我"
  CPU 可以去处理其他协程
  网络响应到达 → 事件循环恢复这个协程


asyncio.to_thread（我们的方案）
═══════════════════════════════════════
await asyncio.to_thread(requests.post, url)   ← 占一个线程！
  事件循环: "线程池，帮我跑这个同步函数"
  线程池线程: 阻塞在 requests.post() 上
  事件循环: 继续处理其他协程
  线程完成 → 事件循环恢复原协程
```

**区别：**
- 真正的异步：0 线程占用，纯事件驱动
- to_thread：每个协程占一个线程（虽然在等 IO 时让出了 CPU）

### 4.2 为什么我们的方案也「够用」

对于 2~3 个 Coder 并行，占 2~3 个线程完全不是问题：

```
2 个 Coder → 2 个线程 → 2 × 8MB = 16MB 内存 → 完全可忽略
```

但如果 100 个 Coder 并行，就有 100 个线程阻塞等待，会出问题。
不过 Day4 用 LangChain 的 `ainvoke()` 就解决了——那是原生 async。

**Java 类比：**
- `to_thread` ≈ `CompletableFuture.supplyAsync(() -> blockingCall(), threadPool)`
- 原生 async ≈ Java 21 虚拟线程（Virtual Thread），阻塞不占 OS 线程

## 五、【刻意踩坑】详解

### 5.1 不写 await —— 协程被丢弃

```python
# orchestrator.py → run_parallel_no_await()
discarded = []
for i in range(len(subtasks)):
    coro = self._coder_async(coders[i], subtasks[i], i + 1)
    discarded.append(coro)   # ← 创建协程对象，但没有 await！
    # coro 只是一个「计划」，没有调度执行
    # 函数返回后 coro 被垃圾回收，里面的任务永远不执行
```

**Python 会给你一个警告：**
```
RuntimeWarning: coroutine 'Orchestrator._coder_async' was never awaited
```

**Java 类比：**
```java
// 相当于创建了 Future 但没调用 .get()，也没交给 executor
var future = CompletableFuture.supplyAsync(() -> doWork());
// 如果没有 executor，这个 future 永远不会执行
```

### 5.2 超时后不保留部分结果

```python
# orchestrator.py → run_parallel_with_timeout()
async def _run_with_timeout():
    try:
        return await asyncio.wait_for(
            asyncio.gather(*tasks),
            timeout=timeout,      # 5 秒超时
        )
    except asyncio.TimeoutError:
        return []                 # ← 全部丢弃！已完成的任务也丢了
```

**正确做法应该是：**
```python
except asyncio.TimeoutError:
    # 收集已完成的部分结果
    partial = [t.result() for t in tasks if t.done() and not t.exception()]
    return partial   # 而不是 return []
```

### 5.3 单任务失败拖垮全部

```python
# orchestrator.py → run_parallel()
codes = await asyncio.gather(*tasks)
# ↑ 如果其中任何一个协程抛异常，整个 gather 抛异常
```

**正确做法：**
```python
codes = await asyncio.gather(*tasks, return_exceptions=True)
# ↑ 异常不会被抛出，而是作为返回值的一部分
# codes = ["代码1", TimeoutError(), "代码3"]
```

### 5.4 输出格式不统一

多个 Coder 并行工作时，各自独立调 LLM，返回的代码格式可能完全不同：

```
Coder1 返回:
```python
def bubble_sort(arr):
    ...
```

Coder2 返回:
def binary_search(arr, target):
    """
    二分查找
    """
    ...
```

合并时不做格式统一，直接拼接。验证 6 就是为了亲眼看到这个现象。

### 5.5 _parse_subtasks 的笨拙

```python
def _parse_subtasks(self, plan_text: str) -> list[str]:
    # 用最简单的正则匹配「### 子任务 N」格式
    parts = re.split(r'(?:###?\s*子任务\s*\d+|【子任务\d】)', plan_text)
    # 然后过滤太短的片段
    subtasks = [p.strip() for p in parts if len(p.strip()) > 30]
    # 问题 1: 正则很脆弱，Planner 换个格式就失效
    # 问题 2: len() > 30 阈值太死，短的合法子任务会被过滤掉
    # 问题 3: 如果什么都没拆出来，直接回退到 [plan_text]
```

## 六、Java 开发者对照表

| Python 概念 | Java 等价 | 说明 |
|------------|----------|------|
| `async def` | —（Java 无原生协程关键字） | 定义协程函数 |
| `await` | `future.get()` 但非阻塞 | 等待异步结果 |
| `asyncio.gather(*tasks)` | `CompletableFuture.allOf(futures).join()` | 等待全部完成 |
| `asyncio.to_thread(fn, arg)` | `CompletableFuture.supplyAsync(() -> fn(arg), executor)` | 线程池执行同步代码 |
| `asyncio.run(coro)` | `future.get()` 阻塞等待 | 桥接 async → sync |
| `*tasks` 解包 | 手动展开 `gather(t[0], t[1], ...)` | Python 特有语法糖 |
| `**kwargs` 解包 | 手动 `.get()` 每个 key | Python 特有语法糖：dict → 关键字参数 |
| `*args` 收拢 | 可变参数 `String... args` | 定义侧：多个参数 → 元组 |
| `asyncio.wait_for(coro, t)` | `future.get(t, TimeUnit.SECONDS)` | 超时控制 |
| `return_exceptions=True` | 异常作为结果返回，不抛 | gather 的安全模式 |
| `RuntimeWarning: coroutine never awaited` | 创建了 Future 但没提交给 executor | 常见踩坑 |

### 实验 3：手动对比 asyncio.gather 两种模式

```python
import asyncio

async def task(name, fail=False):
    await asyncio.sleep(1)
    if fail:
        raise ValueError(f"{name} 失败了!")
    return f"{name} 完成"

async def test_default():
    """默认模式：一个失败全部炸"""
    try:
        results = await asyncio.gather(
            task("A"),
            task("B", fail=True),  # ← 这个会失败
            task("C"),
        )
        print(f"全部成功: {results}")
    except Exception as e:
        print(f"炸了: {e}")
        # 输出: 炸了: B 失败了!
        # A 和 C 的结果全部丢失！

async def test_return_exceptions():
    """安全模式：异常作为结果返回"""
    results = await asyncio.gather(
        task("A"),
        task("B", fail=True),
        task("C"),
        return_exceptions=True,     # ← 关键参数
    )
    for r in results:
        if isinstance(r, Exception):
            print(f"  失败: {r}")
        else:
            print(f"  成功: {r}")
    # 输出: 成功: A 完成  失败: B 失败了!  成功: C 完成

asyncio.run(test_default())
print("---")
asyncio.run(test_return_exceptions())
```
