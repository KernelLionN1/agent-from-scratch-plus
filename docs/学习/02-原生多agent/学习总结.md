## 二、阶段一：角色定义 + 消息总线

### 做了什么

```
AgentRole 枚举：PLANNER / CODER / REVIEWER
   每个角色有独立的 system prompt 和 temperature

MessageBus：Agent 之间通信的通道
   Message(sender, receiver, type, content) 标准格式
   按 receiver 存储消息，支持按类型过滤
```

### 关键概念

| 概念 | 说明 | Java 类比 |
|------|------|----------|
| AgentRole | 枚举角色类型 | `enum Role { PLANNER, CODER, REVIEWER }` |
| RoleConfig | 捆绑 prompt + temperature | `@ConfigurationProperties` |
| MessageBus | 消息队列 | EventBus / MessageQueue |

### 刻意踩坑

| 坑点 | 说明 | 代码位置 |
|------|------|---------|
| 消息重复消费 | `receive()` 只读不删，同一条消息被多次返回 | `message_bus.py:receive()` |
| 角色 Prompt 模糊 | system prompt 没写"你只能做XX不能做YY" | `roles.py:ROLE_PROMPTS` |

## 三、阶段二：串行任务分发

### 做了什么

```
Orchestrator.run_serial():
  步骤1: Planner 拆分    → plan
  步骤2: Coder 编码      → code
  步骤3: Reviewer 审核   → review
  步骤4: Coder 修复      → fixed_code
```

### 关键概念

| 概念 | 说明 |
|------|------|
| BaseAgent 模板方法 | `execute()` 抽象 → 子类实现具体行为 |
| `call_llm()` | 用角色的 system prompt 调 LLM |
| `run_serial()` vs `run_serial_with_bus()` | 直接调用模式 vs 消息总线模式 |

### 刻意踩坑

| 坑点 | 说明 | 验证结果 |
|------|------|---------|
| 任务拆分不合理 | 不约束 Planner 粒度 | 可能拆 1 个或 20 个 |
| 角色越权 | Coder 回答了规划问题 | 验证 6 已复现 |
| 执行顺序混乱 | 不设依赖检查 | Reviewer 可能在 Coder 完成前执行 |

## 四、阶段三：并行执行 + 结果汇总

### 做了什么

```
run_parallel(requirement, n_coders=2):

步骤1: Planner 拆分（串行，10s）
步骤2: 多个 Coder 并行（用 asyncio.gather + to_thread）
        ┌─ coder-1 处理子任务1 (12s) ─┐
        └─ coder-2 处理子任务2 (12s) ─┘
        并行耗时 12s（串行预估 24s）
步骤3: Reviewer 审核汇总代码
```

### 核心概念：asyncio 协程

```
async 函数调用 ≠ 立即执行

coro = _coder_async(coder, subtask, 1)
# ↑ 只是创建协程对象，没有跑！相当于"下订单"

result = await coro
# ↑ 真正执行，等待完成

asyncio.gather(coro1, coro2, coro3)
# ↑ 同时调度，等全部完成

asyncio.to_thread(sync_fn, arg)
# ↑ 把同步函数丢进线程池，伪异步
```

### Nith 的提问记录

| 问题 | 回答 |
|------|------|
| `_` 前缀是什么意思？ | Python 约定：私有方法。不强制，靠社会契约 |
| 为什么 async 函数调用不立即执行？ | 返回协程对象（订单），await 才真正执行（上菜） |
| `*tasks` 是什么？ | 列表解包，`[a,b,c]` → `a, b, c`（位置参数） |
| `**kwargs` 是什么？ | 字典解包，`{k:v}` → `k=v`（关键字参数） |
| 协程数量要提前声明吗？ | 不需要，列表推导式动态生成，gather(*tasks) 自适应 |
| Python 协程 vs Go goroutine？ | Python 显式 await，Go 运行时自动切换 |

### 刻意踩坑

| 坑点 | 说明 | 验证结果 |
|------|------|---------|
| 不写 await | 协程被丢弃，`RuntimeWarning` | ✅ 全部丢失 |
| 输出格式不统一 | 两个 Coder 返回格式不同 | ✅ 确认差异 |
| 超时丢部分结果 | `wait_for` 超时后 `return []` | ⬜ Day3 修 |
| 单任务失败拖垮全部 | `asyncio.gather()` 不做 `return_exceptions` | ⬜ Day3 修 |
| LLM 调用无重试 | `LLMClient.chat()` 裸调 API | ⬜ Day3 修 |
| _parse_subtasks 阈值 | `>30` 字符过滤过严 | ⬜ Day3 修 |

## 五、阶段四：全局状态管理

### 做了什么

```
SharedState:
  _data: dict            ← 实际存储（private）
  _version: int          ← 全局版本号（乐观锁）
  _lock: threading.Lock  ← 互斥锁（并发安全）

三大保护机制：
  1. Lock:       同时只有一个线程读写
  2. 乐观锁:     版本号不匹配则拒绝更新
  3. deepcopy:   get() 返回深拷贝，外部修改不污染内部

便利方法：
  init_progress(n)     → 初始化进度
  mark_task_done(...)  → 标记完成
  snapshot()           → 完整快照
```

### Nith 的理解（三句话总结）

> **理解 1：乐观锁 + 互斥锁** — 对读写都加简单锁，避免同时操作。后来的进程如果版本号不对就拒绝写入，防止过快完成的进程污染了数据。
>
> **理解 2：深拷贝隔离** — 将内存中的对象复制一份副本，外部修改改的是副本，内部原数据不受影响。
>
> **理解 3：裸 dict 的危险** — AI 返回什么就存什么，没有任何格式约束。Agent 可能把原来正常的键值对给换掉，导致后续流程对应不上。

### 这三点在 Day4 的对应

| 手搓痛点 | LangGraph 方案 | 怎么简化的 |
|---------|---------------|-----------|
| Lock + 乐观锁 | 节点间状态隔离，每个节点拿到独立副本 | 不用写锁，框架合并 |
| deepcopy 手动拷贝 | TypedDict + 不可变更新 | 类型系统保证隔离 |
| 裸 dict 被 AI 随意改 | `with_structured_output` + Schema | LLM 输出是类型化对象 |

### 刻意踩坑

| 坑点 | 说明 | 验证结果 |
|------|------|---------|
| 全局变量滥用 | 两个线程无锁改 dict → counter 被覆盖 | ✅ counter=1 ≠ 2 |
| bypass_lock | 绕锁修改，版本号不递增，乐观锁失效 | ✅ 值被覆盖但版本号不变 |
| 版本冲突无重试 | update 返回 False 就完了 | ⬜ Day3 加自动重试 |

| Day2 手搓 | LangGraph 等价 | 说明 |
|-----------|---------------|------|
| `Orchestrator` | `StateGraph` | 编排器 → 状态图 |
