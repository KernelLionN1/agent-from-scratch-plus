## 一、先理解：从单 Agent 到多 Agent 的关键变化

Day1 的 ReAct Agent 是一个人在干活：

```
用户 → Agent(LLM) → 工具 → Agent(LLM) → 答案
         ↑ 思考 + 行动 + 观察 都在一个循环里
```

Day2 的多 Agent 是把一个人拆成三个：

```
用户 → Planner → Coder → Reviewer → Coder(修复) → 结果
       规划      编码     审核        修复
```

**关键变化：**
1. 每个 Agent 有自己的 system prompt（角色人格）
2. Agent 之间通过 MessageBus 通信（不是直接调用）
3. Orchestrator 编排执行顺序（代替 Day1 的 while 循环）

## 二、核心概念：BaseAgent 基类

### 2.1 设计思想

三个 Agent（Planner / Coder / Reviewer）有共同行为：
- 都需要调用 LLM
- 都需要从 MessageBus 收发消息
- 都有自己的角色配置

所以提取出一个 `BaseAgent` 基类：

```python
class BaseAgent:
    def __init__(self, bus, name, role):
        self.name = name        # Agent 标识
        self.role = role        # 角色枚举
        self.config = get_role_config(role)  # prompt + temperature
        self.llm = LLMClient()  # LLM 客户端
        self.bus = bus          # 共享消息总线

    def execute(self, input_text):  # 子类必须重写
        raise NotImplementedError

    def call_llm(self, prompt):     # 用角色的 system prompt 调 LLM
        ...
```

**Java 类比：** 相当于 Spring 里的 AbstractService 模板类，子类实现 `execute()` 抽象方法。

### 2.2 继承关系

```
BaseAgent (抽象基类)
  ├── PlannerAgent   → execute() = 拆分需求为子任务
  ├── CoderAgent     → execute() = 任务描述 → 代码
  │   └── fix_code() → 根据审核意见修代码
  └── ReviewerAgent  → execute() = 代码 → 审核意见
```

### 2.3 call_llm() 做了什么事？

```python
def call_llm(self, user_prompt: str, extra_context: str = "") -> str:
    messages = [
        {"role": "system", "content": self.config.prompt},  # 角色人格
        {"role": "user",   "content": user_prompt},         # 具体任务
    ]
    response = self.llm.chat(messages=messages, temperature=self.config.temperature)
    return response["content"]
```

**和 Day1 的区别：**
- Day1 的 system prompt 是通用的「你是一个有用的 AI 助手」
- Day2 的 system prompt 是按角色定制的（Planner 用规划专家 prompt，Coder 用编程专家 prompt）
- Day2 不传 tools——这些 Agent 不需要调用工具，只需要生成文本

## 三、核心概念：串行编排（Orchestrator）

### 3.1 流程

```
run_serial(requirement)
  │
  ├─ 步骤1: planner.execute(requirement)
  │    └─ 返回: 子任务列表（文本）
  │
  ├─ 步骤2: coder.execute(plan)
  │    └─ 返回: Python 代码
  │
  ├─ 步骤3: reviewer.execute(code)
  │    └─ 返回: 审核意见
  │
  └─ 步骤4: coder.fix_code(review)     ← 可选
       └─ 返回: 修复后的代码
```

### 3.2 和 Day1 ReAct 循环的对比

| | Day1 ReAct Agent | Day2 Orchestrator |
|---|---|---|
| 执行模式 | LLM 自主决策循环 | 固定顺序编排 |
| 工具调用 | 支持（calculator/text_query） | 不支持 |
| 角色 | 一个通用 Agent | 三个分工 Agent |
| 通信 | 无（单进程内） | MessageBus |
| 灵活性 | 高（LLM 决定何时停止） | 低（固定 4 步） |

**Java 类比：** 
- Day1 相当于一个状态机（while 循环 + 条件判断）
- Day2 相当于一个工作流引擎（固定步骤，按序执行）

### 3.3 两种调用模式

**模式 A：直接调用（run_serial）**
```python
result = orch.run_serial("实现排序算法")
# Orchestrator 直接调用 planner.execute() → coder.execute() → ...
# 快速、简单，但 Agent 之间没有真正"通信"
```

**模式 B：消息总线调用（run_serial_with_bus）**
```python
result = orch.run_serial_with_bus("实现排序算法")
# Agents 通过 MessageBus 传递消息
# 更接近真实分布式系统的通信方式
```

## 五、【刻意踩坑】详解

### 5.1 任务拆分不合理

```python
# planner.py —— prompt 只说了"拆分子任务"
# 没有限制：
# - 最少/最多几个子任务
# - 每个子任务的详细程度
# - 输出格式（JSON/YAML/编号列表）
```

**实际观察（验证 5）：** Planner 拆了 4 个子任务，粒度合理。但如果需求更复杂（比如「做一个电商系统」），Planner 可能拆出 20 个微任务或 1 个粗任务，没有任何约束。

### 5.2 角色越权（验证 6 已复现）

问 Coder 一个规划问题：

```
输入: "请帮我规划一个完整的 Web 应用项目，包括需要的模块、技术选型和开发步骤。"
```

**Coder 的回答：** 「我来为您规划一个完整的 Web 应用项目框架。技术选型：FastAPI + PostgreSQL + Redis...」

这是越权——Coder 的职责是写代码，不是规划项目。但因为 system prompt 里没写「你只能编码不能规划」，所以 Coder 很自然地越权了。

### 5.3 输出格式不统一

Planner、Coder、Reviewer 的输出都是纯文本，没有固定格式：

- Planner 用 Markdown 标题（`### 子任务 1`）
- Coder 用代码块（` ```python `）
- Reviewer 用自然语言段落

下游解析这些输出时就很痛苦——Day3 统一加 JSON Schema 约束。

## 六、Java 开发者对照表

| Python 概念 | Java 等价 | 说明 |
|------------|----------|------|
| `BaseAgent` 抽象类 | `abstract class AbstractService` | 模板方法模式 |
| `execute()` 抽象方法 | `abstract String execute(String input)` | 子类必须实现 |
| `call_llm()` | `protected String callLLM(...)` | 父类提供的通用方法 |
| `Orchestrator` | `@Service class WorkflowEngine` | 编排多个 Service |
| `run_serial()` | 顺序调用 → `service1.process()` → `service2.process()` | 同步执行 |
| `super().__init__(...)` | `super(bus, name, role)` | 调用父类构造器 |
| 消息传递 vs 直接调用 | EventBus vs @Autowired 直接注入 | 解耦 vs 简单 |

## 七、动手实验

### 实验 1：观察不同复杂度的拆分

```python
from src.message_bus import MessageBus
from src.agents import PlannerAgent

bus = MessageBus()
planner = PlannerAgent(bus)

# 简单需求
print("=== 简单需求 ===")
print(planner.execute("写一个 hello world"))

# 复杂需求
print("\n=== 复杂需求 ===")
print(planner.execute("做一个完整的博客系统，包括用户注册、文章发布、评论、搜索"))
```

对比两次输出，看 Planner 的拆分粒度差异有多大。

### 实验 2：只跑一半流程

```python
from src.orchestrator import Orchestrator
from src.message_bus import MessageBus

bus = MessageBus()
orch = Orchestrator(bus)

result = orch.run_serial("实现二分查找", with_fix=False)
# with_fix=False → 跳过修复步骤
# 对比审核前后的代码，看 Reviewer 发现了什么问题
```

### 实验 3：用消息总线模式跑

```python
bus = MessageBus()
orch = Orchestrator(bus)

result1 = orch.run_serial("实现快速排序")
bus.clear()
result2 = orch.run_serial_with_bus("实现快速排序")

# 对比两种模式的输出
# 直接调用：快速，Agent 之间不经过总线
# 消息模式：通过总线传递，可以看到每条消息的路径
```

## 八、阶段二小结

| 学到了什么 | 对应知识点 |
|-----------|----------|
