## 一、先理解：为什么 Day1 的坑要现在修？

Day1 的目标是"先跑通"，所以刻意保留了大量问题。Day3 是从"教学原型"到"可用的系统"的关键一步。

```
Day1 状态：能跑，但...
  ├── eval() 直接执行任意代码 → 安全性为 0
  ├── 工具返回 dict → LLM 收到 `{'python': '...'}` 不知道是什么
  ├── system prompt 太温柔 → LLM 可能不用工具就直接回答
  ├── while True 无上限 → 如果 LLM 陷入循环永远不会停
  ├── 全局 agent 共享 → 用户 A 和用户 B 的 memory 互相污染
  └── 同步阻塞 → 一个请求卡住，其他请求全排队

Day3 目标：每个问题都有明确的防护机制
  ├── eval() → ast.literal_eval()（只解析字面量）
  ├── 工具返回 → 格式化文本（人类和 LLM 都能理解）
  ├── system prompt → 明确"必须调工具"
  ├── while True → max_iterations 硬上限
  └── 全局 agent → 请求级实例 + async 隔离
```

## 二、9 个踩坑逐个修复

### 2.1 坑 #1：eval() 安全漏洞 — `tools.py`

**当前代码（危险）：**
```python
def calculator(expression: str) -> float:
    return eval(expression)
    # eval("__import__('os').system('rm -rf /')")  ← 能执行任意代码！
```

**修复方案：`ast.literal_eval()`**
```python
import ast

def calculator(expression: str) -> float:
    # ast.literal_eval() 只解析 Python 字面量：
    #   数字: 123, 3.14
    #   字符串: "hello"
    #   元组/列表/字典: (1,2), [1,2], {"a":1}
    #   四则运算: 1 + 2 * 3  ← 不支持，只支持字面量！
    #
    # 所以 literal_eval 对数学表达式不够用 ——
    # 我们需要额外做一个安全校验
    return _safe_eval(expression)

def _safe_eval(expr: str) -> float:
    """只允许数字、运算符、括号、空格的数学表达式"""
    import re
    # 白名单校验：只允许 0-9 . + - * / ** ( ) 空格
    if not re.match(r'^[\d\s\+\-\*\/\(\)\.\%\^]+$', expr):
        raise ValueError(f"不安全的表达式: {expr}")
    # 安全字符校验通过后，用 eval 计算
    # 注意：这种方案仍然不是 100% 安全（理论上可能被绕过），
    # 生产环境建议用专门的数学表达式解析器
    return eval(expr, {"__builtins__": {}}, {})
    #                     ↑ 禁止所有内置函数，eval 只能做纯数学运算
```

**Java 类比：**
```java
// Java 里没有 eval，但 ScriptEngine 有类似问题
ScriptEngine engine = new ScriptEngineManager().getEngineByName("js");
engine.eval("Runtime.getRuntime().exec('rm -rf /')");  // ← 同样危险

// 正确做法：用专门的表达式解析器
double result = new ExpressionParser("1+2*3").evaluate();
```

### 2.2 坑 #2：工具返回 dict 非字符串 — `tools.py`

**当前代码（不友好）：**
```python
def search_knowledge(query: str) -> dict:
    # 返回 {"python": "Python 是一门..."}
    return result  # dict → str() → "{'python': '...'}"  ← LLM 还得二次解析
```

**修复方案：返回格式化文本**
```python
def search_knowledge(query: str) -> str:  # ← 返回类型从 dict 改为 str
    """从知识库搜索，返回格式化文本"""
    result = {}
    for key, value in _KNOWLEDGE_BASE.items():
        if query.lower() in key.lower() or query.lower() in value.lower():
            result[key] = value
    
    if not result:
        return f"未找到与 '{query}' 相关的知识。"
    
    # 格式化成 LLM 容易理解的文本
    lines = [f"搜索 '{query}' 的结果："]
    for key, value in result.items():
        lines.append(f"  [{key}]: {value}")
    return "\n".join(lines)
```

**关键理解：LLM 不是程序，是人。**
- `{"python": "..."}` → LLM 要"看懂"这个 JSON 结构需要额外的认知负荷
- `[python]: Python 是一门...` → 一目了然

### 2.5 坑 #5：工具结果无校验/重试 — `agent.py`

**当前代码：**
```python
for tc in response["tool_calls"]:
    tool_name = tc["name"]
    tool_args = json.loads(tc["arguments"])
    tool_result = execute_tool(tool_name, tool_args)
    self.memory.add_tool_result(...)  # ← 直接存入，不管成功还是失败
```

**修复方案：校验工具结果，记录到 memory 让 LLM 基于错误重试**
```python
for tc in response["tool_calls"]:
    try:
        tool_args = json.loads(tc["arguments"])
    except json.JSONDecodeError as e:
        # LLM 传的 arguments 不是合法 JSON
        self.memory.add_tool_result(
            tool_call_id=tc["id"],
            tool_name=tc["name"],
            result=f"工具参数解析失败: {e}。请用正确的 JSON 格式重试。"
        )
        continue
    
    # 判断工具是否存在
    if tc["name"] not in TOOL_REGISTRY:
        self.memory.add_tool_result(
            tool_call_id=tc["id"],
            tool_name=tc["name"],
            result=f"Error: 未知工具 '{tc['name']}'。可用工具: {list_tools()}"
        )
        continue
    
    # 执行工具
    try:
        tool_result = execute_tool(tc["name"], tool_args)
    except Exception as e:
        # 工具执行异常 → 把错误信息反馈给 LLM，让它自己决定怎么办
        tool_result = f"工具执行失败: {type(e).__name__}: {e}"
    
    self.memory.add_tool_result(
        tool_call_id=tc["id"],
        tool_name=tc["name"],
        result=str(tool_result),
    )
```

**核心思路：** 不替 LLM 决定"要不要重试"，而是把错误信息原样反馈，让 LLM 基于 ReAct 循环自己判断。

### 2.7 坑 #7：token 估算不准 — `memory.py`

**当前代码：**
```python
def _estimate_tokens(self, messages: list[dict]) -> int:
    total_chars = sum(len(msg.get("content", "") or "") for msg in messages)
    return total_chars // 4  # ← 极其粗糙
```

**修复：**
```python
def _estimate_tokens(self, messages: list[dict]) -> int:
    """Token 数量估算 —— 改进版，中文友好"""
    total_chars = 0
    for msg in messages:
        content = msg.get("content", "") or ""
        # 分别统计中英文字符
        chinese_chars = sum(1 for c in content if '\u4e00' <= c <= '\u9fff')
        other_chars = len(content) - chinese_chars
        # 中文约 0.5-1 token/字，英文约 0.25 token/字
        # 取中值：中文 0.7，英文 0.25
        total_chars = chinese_chars * 0.7 + other_chars * 0.25
        
        if msg.get("tool_calls"):
            total_chars += len(str(msg["tool_calls"])) * 0.25
    
    return int(total_chars)
    # ⚠️ 注意：这仍然是估算！精确计算需用 tiktoken 库
```

### 2.8 坑 #8：全局 agent 实例共享 — `api.py`

**当前问题：**
```python
# 模块级全局变量 —— 所有请求共享！
agent = ReActAgent(max_iterations=10, truncation_strategy="none")

@app.post("/chat")
def chat(request: ChatRequest):
    answer = agent.run(request.message)  # ← 并发时 memory 互相污染
```

**修复方案：请求级实例**
```python
# 不再创建全局 agent，改为工厂函数
def create_agent() -> ReActAgent:
    """每个请求创建一个新的 Agent 实例"""
    return ReActAgent(max_iterations=10, truncation_strategy="none")

@app.post("/chat")
def chat(request: ChatRequest):
    agent = create_agent()  # ← 请求级隔离
    answer = agent.run(request.message)
```

### 2.9 坑 #9：同步阻塞 + 无超时 — `api.py`

**当前问题：**
```python
@app.post("/chat")
def chat(request: ChatRequest):  # ← 同步 def，阻塞事件循环
    answer = agent.run(request.message)  # ← 可能卡住几分钟
```

**修复方案：async + to_thread + 超时**
```python
import asyncio

@app.post("/chat")
async def chat(request: ChatRequest):  # ← async def，不阻塞事件循环
    try:
        agent = create_agent()
        # asyncio.to_thread: 把同步的 agent.run() 丢进线程池
        # asyncio.wait_for: 加 60 秒超时保护
        answer = await asyncio.wait_for(
            asyncio.to_thread(agent.run, request.message),
            timeout=60.0
        )
        return ChatResponse(answer=answer, status="ok")
    except asyncio.TimeoutError:
        raise HTTPException(status_code=504, detail="请求超时，请简化问题后重试")
    except Exception as e:
        raise HTTPException(status_code=500, detail=f"Agent 错误: {str(e)}")
```

## 三、Java 开发者对照表

| Python 概念 | Java 等价 | 说明 |
|------------|----------|------|
| `ast.literal_eval()` | 自定义 `ExpressionParser` | Python 有内置的安全解析器 |
| `eval(expr, {"__builtins__": {}}, {})` | — | 限制命名空间的 eval，Java 无等价物 |
| `async def` + `asyncio.to_thread` | `@Async` + `CompletableFuture.supplyAsync()` | 异步包装同步代码 |
| `asyncio.wait_for(coro, timeout)` | `future.get(timeout, TimeUnit.SECONDS)` | 超时控制 |
| `json.JSONDecodeError` | `JsonParseException` | JSON 解析异常 |
| `\u4e00` ~ `\u9fff` | `Character.isIdeographic()` | 中文字符范围判断 |
| 请求级实例 | `@RequestScope` | Spring 的请求作用域 |

### 实验 2：对比全局 vs 请求级 agent

```python
import asyncio
from src.api import create_agent

# 模拟两个"用户"同时发请求
async def user_a():
    agent = create_agent()
    return agent.run("我叫张三")

async def user_b():
    agent = create_agent()
    return agent.run("我叫什么名字？")

async def main():
    r1, r2 = await asyncio.gather(user_a(), user_b())
    print(f"用户A: {r1}")
    print(f"用户B: {r2}")
    # 修复后：用户B 不知道用户A 的名字（隔离正常）

asyncio.run(main())
```
