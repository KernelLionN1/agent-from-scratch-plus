> 对应代码：`src/dynamic_agent.py`（301 行）  
> 前置知识：Day4 固定工作流 StateGraph  
> 核心问题：怎么让 LLM 自己决定下一步，而不是程序员写死？

---

## 一、Day4 vs Day5：固定边 vs LLM 自主决策

```
Day4（固定工作流）:                  Day5（LLM 动态路由）:
                                      ┌──────────────────┐
planner → coder → reviewer → END      │                  ↓
边的方向是程序员决定的                  agent ──(LLM判断)──→ tools
     ↕                                     │
add_edge("planner", "coder")               └──→ END
add_edge("coder", "reviewer")                      ↕
                                            should_continue(state)
区别: "coder 之后一定走 reviewer"          区别: "LLM 说调 tool 就走 tool，
       ← 写死在 add_edge 里                      LLM 说结束就结束"
```

**核心变化：** 从 `add_edge`（固定边）到 `add_conditional_edges`（条件边）。条件边每次执行时调一个函数，函数返回值决定走哪条路。这个函数里看的不是 if/else，而是 **LLM 返回的 tool_calls**。

**同一个输入，两次调用可能走不同路径：**
```
用户："计算 100+200"
  调用1: agent → LLM调calculator → tools → agent → END（2步）
  调用2: agent → LLM调calculator → tools → agent → LLM又调 → tools → agent → END（3步）
```
LLM 的"脾气"不同，走的步数就不同。这就是"动态路由"。

## 二、代码逐步解读

### 2.1 AgentState —— 图的共享内存

```python
class AgentState(TypedDict):
    input: str                        # 用户输入（只在初始时用）
    messages: Annotated[list, add]    # 对话历史（自动追加，不覆盖）
    tool_results: Annotated[list, add] # 工具执行结果历史（自动追加）
    final_answer: str                 # 最终回复
    steps: int                        # 已执行步数（agent_node 每次+1）
    max_steps: int                    # 最大步数（防死循环）
```

**关键：`Annotated[list, add]`**

```python
from operator import add
messages: Annotated[list, add]

# 等价于：每次节点返回 {"messages": [...]} 时，自动执行 state["messages"] + 新消息
# 对比普通 dict 更新：普通更新是覆盖（旧值丢失），add 是拼接（旧值保留）
# Java 类比：List.addAll() vs List = newList
```

**面试常问：** LangGraph 的 reducer 机制 —— `Annotated` 的第二个参数是 reducer 函数，每次节点更新该字段时执行。`add` 是 operator 里的列表拼接函数。你也可以自定义 reducer，比如 `operator.add` 用于数字累加。

### 2.2 agent_node —— LLM 思考节点

```python
def agent_node(state: AgentState, llm: LLMClient, tools: list) -> dict:
    # 1. 构建消息列表
    messages = [system_msg]  # system prompt 开头

    # 2. 【踩坑修复】初始 messages 为空时，从 state["input"] 取用户问题
    history = state.get("messages", [])
    if not history and state.get("input"):
        messages.append({"role": "user", "content": state["input"]})

    for msg in history:       # 把之前的对话历史追加上去
        messages.append(msg)

    # 3. 调 LLM
    response = llm.chat(messages=messages, tools=tools)

    # 4. 构建这次要追加到 state 的消息
    new_messages = [{"role": "assistant", "content": response["content"]}]
    if response.get("tool_calls"):  # LLM 想调工具！
        for tc in response["tool_calls"]:
            new_messages.append({
                "role": "assistant",
                "tool_calls": [{"id": tc["id"], "function": {"name": tc["name"], "arguments": tc["arguments"]}}],
            })

    return {"messages": new_messages, "steps": state["steps"] + 1}
```

**这段代码揭示的核心流程：**
1. agent 节点调 LLM
2. LLM 返回两种结果：纯文本（"结果是300"）或 tool_calls（"我要调calculator"）
3. `should_continue()` 根据返回类型决定下一步

### 2.3 tool_node —— 工具执行节点

```python
def tool_node(state: AgentState) -> dict:
    # 从最后一条消息提取 tool_calls
    last_msg = state["messages"][-1]
    tool_calls = last_msg.get("tool_calls", [])

    for tc in tool_calls:
        fn = tc.get("function", tc)
        name = fn.get("name", "unknown")          # 工具名
        args_str = fn.get("arguments", "{}")       # 工具参数（JSON字符串）
        args = json.loads(args_str)                # 解析JSON

        # 【踩坑修复】DeepSeek 可能用 kwargs 包装参数
        if isinstance(args, dict) and "kwargs" in args and len(args) == 1:
            args = args["kwargs"]

        result = execute_tool(name, args)          # 实际执行工具

        results.append({
            "role": "tool",
            "content": str(result),
            "tool_call_id": tc.get("id", ""),
        })

    return {"messages": results, "tool_results": [r["content"] for r in results]}
```

**工具执行后的消息追加到 messages → agent 节点再次被调用 → LLM 看到工具结果 → 决定下一步。**

### 2.4 should_continue —— 路由函数（核心！）

```python
def should_continue(state: AgentState) -> Literal["tools", "end"]:
    # 步数保护：超过 max_steps 强制退出
    if state["steps"] >= state.get("max_steps", 10):
        return "end"

    last_msg = state["messages"][-1]
    if isinstance(last_msg, dict) and last_msg.get("tool_calls"):
        return "tools"    # LLM 想调工具 → 走 tools 节点
    return "end"          # LLM 没调工具 → 结束
```

**这是整个动态路由的关键 —— 没有 if/else 硬编码规则。只看 LLM 返回了什么。**

```
执行轨迹：
Step 0: DEBUG (agent) → LLM 返回 tool_calls → should_continue → "tools"
Step 1: tools → 执行 calculator → 回到 agent
Step 2: DEBUG (agent) → LLM 看到结果"300" → 返回纯文本 → should_continue → "end"
```

`Literal["tools", "end"]` 是 Python 类型提示，告诉类型检查器这个函数只返回这两个字符串。`add_conditional_edges` 里的映射 `{"tools": "tools", "end": END}` 把这两个返回值映射到实际节点。

### 2.5 build_dynamic_graph —— 图构建

```python
def build_dynamic_graph(llm: LLMClient) -> StateGraph:
    graph = StateGraph(AgentState)

    graph.add_node("agent", lambda s: agent_node(s, llm, tools))
    graph.add_node("tools", tool_node)

    graph.set_entry_point("agent")

    # *** 动态路由：条件边 ***
    graph.add_conditional_edges(
        "agent",
        should_continue,           # 每次从 agent 出发时，调这个函数决定去哪
        {"tools": "tools", "end": END},  # 返回值 → 目标节点
    )

    # 固定边：工具执行完一定回到 agent
    graph.add_edge("tools", "agent")

    return graph
```

**Day4 对比：**
```python
# Day4（固定边）
graph.add_edge("planner", "coder")     # 程序员说：planner之后一定是coder
graph.add_edge("coder", "reviewer")    # 程序员说：coder之后一定是reviewer

# Day5（条件边）
graph.add_conditional_edges("agent", should_continue, ...)
# LLM 说：agent之后走tools还是END，由我决定
```

### 2.6 DynamicAgent —— 对外接口

```python
class DynamicAgent:
    def __init__(self, max_steps: int = 10):
        self.llm = LLMClient()
        self.max_steps = max_steps

    def run(self, user_input: str) -> dict:
        graph = build_dynamic_graph(self.llm)
        app = graph.compile()
        result = app.invoke({"input": user_input, ...})

        # 从 messages 中提取最终回复（最后一个没有 tool_calls 的 assistant 消息）
        for msg in reversed(result["messages"]):
            if msg.get("role") == "assistant" and not msg.get("tool_calls"):
                answer = msg["content"]
                break

        return {"answer": answer, "steps": result["steps"], ...}
```

## 三、踩坑分析（3 个踩坑）

### 踩坑 1：`state["input"]` 未传给 LLM

**现象：** 测试 1b 失败，LLM 不调工具。

**原因：** `agent_node` 只从 `state["messages"]` 构建消息列表。初始 `messages` 为空，用户输入存在 `state["input"]` 里但从未被读取。LLM 只看到 system prompt，不知道用户问了什么 → 返回"好的，请问你需要什么帮助？"

**修复（`agent_node:69-75`）：**
```python
history = state.get("messages", [])
if not history and state.get("input"):
    messages.append({"role": "user", "content": state["input"]})
```

**教训：** LangGraph 的 State 里不同字段的职责要分清楚。`input` 是启动参数，`messages` 是对话流。节点函数需要自己把 `input` 转成第一条 user 消息。

### 踩坑 2：DeepSeek 的 kwargs 参数包装

**现象：**
```
🔧 执行工具: calculator({'kwargs': {'expression': '100+200'}})
📤 结果: TypeError: calculator() got an unexpected keyword argument 'kwargs'
```

**原因：** DeepSeek 的函数调用格式与 OpenAI 公有差异，首次调用可能把参数包在 `{"kwargs": {...}}` 里。

**修复（`tool_node:130-135`）：**
```python
if isinstance(args, dict) and "kwargs" in args and len(args) == 1:
    args = args["kwargs"]
```

**教训：** 不同 LLM 厂商的函数调用格式有差异。生产代码需要做参数格式兼容层。好消息是 DeepSeek 第二次调用会自动纠正格式。

### 踩坑 3：`tool_results` 不用 `Annotated[list, add]`

**现象：** 多轮工具执行后 `tool_results` 只保留最后一次的结果。

**原因：** `tool_results: list[str]` 是普通字段，节点返回 `{"tool_results": [...]}` 时覆盖旧值。`messages` 用了 `Annotated[list, add]`，每次追加而不是覆盖。

**修复（`AgentState:35`）：**
```python
tool_results: Annotated[list, add]  # list → Annotated[list, add]
```

## 四、Java 对照

| Python | Java | 说明 |
|--------|------|------|
| `StateGraph(AgentState)` | `StateMachineBuilder<AgentState>` | 图 = 状态机 |
| `add_node("agent", fn)` | `builder.addState("agent", action)` | 注册节点 |
| `add_conditional_edges("agent", guard, map)` | `builder.addChoice("agent", guard, outcomes)` | 条件边 = Choice + Guard |
| `should_continue(state)` | `Guard.evaluate(context)` | 路由函数 = Guard |
| `Annotated[list, add]` | `List.addAll()` 而非 `list = newList` | 追加而非覆盖 |
| `graph.compile()` | `builder.build()` / `machine.start()` | 编译执行 |
| `app.invoke(state)` | `machine.send(event)` | 触发执行 |
| `add_edge("tools", "agent")` | `builder.addTransition("tools", "agent")` | 固定转移 |
| `agent → tools → agent` 循环 | `WhileLoopChoice` 或自循环状态 | 循环是"回到自己" |
| `Literal["tools", "end"]` | `enum Outcome { TOOLS, END }` | 返回类型约束 |
| `import json` 在函数内部 | — | Python 允许函数内 import（懒加载、减少启动开销） |

## 七、核心概念回顾

| 概念 | 一句话解释 |
|------|-----------|
| 固定边 (`add_edge`) | 程序员决定 A 之后一定走 B |
| 条件边 (`add_conditional_edges`) | 每次执行时调函数，函数返回值决定走哪 |
| 路由函数 (`should_continue`) | 只看 LLM 有没有返回 tool_calls |
| `Annotated[list, add]` | State 字段自动追加而非覆盖 |
| `Literal["tools", "end"]` | 类型提示约束返回值只能是这两个字符串 |
| `graph.compile()` | 编译图结构，校验拓扑，缓存执行计划 |
| `app.invoke(state)` | 从 entry point 开始运行直到 END |

## 八、面试准备

**Q：什么是 LangGraph 的条件边？**
> 条件边（conditional edge）是在运行时动态决定走哪条路，而不是编译时写死。通过 `should_continue(state)` 函数，每次执行时根据当前状态决定下一步。DDay5 中这个函数的判断依据是：LLM 返回了 tool_calls → 走 tools 节点；LLM 返回纯文本 → 走 END。

**Q：`Annotated[list, add]` 是什么意思？**
> LangGraph 的 reducer 机制。普通 State 字段更新时覆盖旧值，但用 `Annotated[list, add]` 标记后，每次节点返回消息列表时执行 `state["messages"] + new_messages`（追加而非覆盖）。`add` 来自 `operator.add`，本质是列表拼接。

**Q：为什么不用 `add_edge("agent", "tools")` 固定死？**
> 因为 LLM 有时需要调工具，有时不需要。固定边意味着 agent 之后一定走 tools，但"说你好"这种简单问题不需要调工具。条件边的设计让 LLM 实时决策流程，实现真正的自主 Agent。

**Q：路由函数在 SAA（手搓 Agent）中也能实现吗？**
> 完全可以！Day1 的 `while True` 循环本质就是路由逻辑：
> ```python
> for i in range(max_iterations):
>     response = llm.chat(messages)
>     if response.get("tool_calls"):   # ← 这就是 should_continue!
>         execute_tool(...)
>         continue                     # ← 相当于 add_edge("tools", "agent")
>     else:
>         return response["content"]   # ← 相当于 return "end"
> ```
> 
> **手搓版 vs LangGraph 版对比：**
> 
> | 手搓版 | LangGraph 版 | 说明 |
> |--------|-------------|------|
> | `for i in range(max_iterations)` | `should_continue` 里 `if steps >= max_steps` | 步数保护 |
> | `if response.get("tool_calls")` | `if last_msg.get("tool_calls")` | 判断是否调工具 |
> | `continue` | `add_edge("tools", "agent")` | 工具执行后回到 agent |
> | `return` | `return "end"` | 结束 |
> 
> **本质完全一样。** LangGraph 只是把这个逻辑用图的节点和边表达出来，而不是 `while` + `if`。LangGraph 的额外好处：可视化、可组合多分支、checkpoint 暂停/恢复、每步 state 可追踪。
