## 一、为什么需要持久化

```
Day4（InMemory）:                    Day5（SQLite）:
                                    ┌────────────────────┐
进程运行: 消息在内存中                │ 消息写入磁盘         │
进程终止: 全部丢失 ❌                  │ 进程重启 → 数据恢复 ✅ │
重启后: "你是谁？我不认识你"          │ 重启后: "上次聊到Python装饰器"│
                                    └────────────────────┘
```

**InMemory 的问题：**
- 进程重启 → 消息全丢
- 不能跨进程共享
- 没有审计/回溯能力

**SQLite 解决的：**
- 持久化存储，重启不丢失
- 多会话隔离（按 session_id）
- 成本追踪（每次 LLM 调用的 token 消耗入库）

## 二、SQLiteChatMessageHistory —— 持久化消息存储

### 2.1 接口设计

与 `InMemoryChatMessageHistory` 接口完全一致：

```python
# InMemory版
from langchain_core.chat_history import InMemoryChatMessageHistory
store = InMemoryChatMessageHistory()
store.add_message(HumanMessage("你好"))
store.messages  # → [HumanMessage("你好")]

# SQLite版（Day5）
from src.memory import SQLiteChatMessageHistory
store = SQLiteChatMessageHistory(session_id="abc-123")
store.add_message({"role": "user", "content": "你好"})  # 也支持 LangChain 对象
store.messages  # → [HumanMessage("你好")]
store.clear()   # 清空当前会话
```

### 2.2 数据库 Schema

```sql
-- 消息表：每行一条对话消息
CREATE TABLE messages (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL,    -- 会话隔离的关键字段
    role          TEXT NOT NULL,    -- user / assistant / tool / system
    content       TEXT,             -- 消息正文
    tool_calls    TEXT,             -- JSON: 工具调用列表
    tool_call_id  TEXT,             -- 工具消息的回溯ID
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**注意：** `tool_calls` 存的是 JSON 字符串（不是 Python 对象），写入时 `json.dumps()`，读取时 `json.loads()`。

### 2.3 与 ConversationMemory 配合

```python
from src.memory import SQLiteChatMessageHistory, ConversationMemory

# 创建 SQLite 后端
history = SQLiteChatMessageHistory(session_id="my-session")

# 传给 ConversationMemory（Day5 新增 history_backend 参数）
mem = ConversationMemory(
    max_messages=20,
    max_tokens=4000,
    history_backend=history,  # ← 关键：指定持久化后端
)

# 后续操作不变
mem.add_user("计算 1+1")
mem.add_assistant("结果是2")
mem.get_messages("sliding_window")  # 截断策略照常工作
```

## 三、SessionManager —— 多会话生命周期管理

### 3.1 核心 API

```python
from src.session import SessionManager

sm = SessionManager()

# 1. 创建会话
sid = sm.create("学习LangGraph")    # → UUID

# 2. 切换到该会话（后续操作都在这个会话下）
sm.switch(sid)

# 3. 获取消息历史 → 传给 ConversationMemory
history = sm.get_history()          # 当前活跃会话的记忆
# 或一步到位
mem = sm.get_memory(max_messages=30, max_tokens=4000)

# 4. 列出所有会话（含消息数和token统计）
for s in sm.list_sessions():
    print(f"{s['name']}: {s['msg_count']}条消息, {s['token_total']}tokens")

# 5. 删除会话（含所有消息+token记录）
sm.delete(sid)  # 也会删除关联的 messages 和 token_usage
```

### 3.2 会话隔离验证

```python
# 两个独立会话，消息互不干扰
s1 = sm.create("数学问题")
s2 = sm.create("编程问题")

sm.switch(s1)
sm.get_history().add_message({"role": "user", "content": "1+1=?"})

sm.switch(s2)
sm.get_history().add_message({"role": "user", "content": "Python装饰器是什么?"})

sm.switch(s1)
print(sm.get_history().count_messages())  # → 1（不是2）
# s1 里只有数学问题的消息，编程问题的消息在 s2 里
```

### 3.3 数据库 Schema（完整）

```sql
-- 会话表
CREATE TABLE sessions (
    id          TEXT PRIMARY KEY,       -- UUID4
    name        TEXT,                   -- 会话名称
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP               -- 最后活跃时间
);

-- 成本追踪表
CREATE TABLE token_usage (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id        TEXT NOT NULL,
    prompt_tokens     INTEGER DEFAULT 0,
    completion_tokens INTEGER DEFAULT 0,
    total_tokens      INTEGER DEFAULT 0,
    model             TEXT DEFAULT '',
    created_at        TIMESTAMP
);
```

## 四、成本追踪

### 4.1 使用方式

每次 LLM 调用后调用 `record_usage()`：

```python
# LLMClient.chat() 返回的 dict 里有 usage 字段
response = llm.chat(messages, tools)
# response = {"content": "...", "tool_calls": [...], "usage": {"prompt_tokens": 150, "completion_tokens": 50, "total_tokens": 200}}

sm.record_usage(session_id, response["usage"], model="deepseek-chat")
```

### 4.2 查询统计

```python
# 单会话统计
stats = sm.get_cost_stats(session_id)
# → {"total_calls": 5, "total_tokens": 1250, "prompt_tokens": 900, "completion_tokens": 350}

# 全局统计
global_stats = sm.get_cost_stats()
# → 所有会话的累计
```

## 八、扩展讨论

### 8.1 数据清洗：Java 大数据 vs Python

Agent 场景下选 Python。不是 Python 更强，是"同语言"的优势：

```
Agent(Python) → 同进程调 pandas/polars → 直接喂给 embedding
   vs
Agent(Python) → HTTP/消息队列 → Spark(Java) → HTTP → Agent(Python)
   3 次网络跳转 + 序列化 × N 条数据 = 巨慢
```

| 场景 | 工具 | 原因 |
|------|------|------|
| Agent 实时清洗（单条/小批） | Python pandas/polars | 同进程，免序列化 |
| 历史数据批量清理（TB级） | Spark（Java/Scala） | 分布式算力 |
| 定时 ETL 管道 | n8n / Airflow（调 Python 脚本） | 工作流编排 |

### 8.2 SQLite 里大量用 TEXT 有影响吗？

**没有。** SQLite 的 TEXT 是变长存储类，不像 MySQL 的 CHAR(255) 是定长。写 VARCHAR(100) 和 TEXT 在 SQLite 内部完全一样——都是变长字符串。真正该关心的是**索引**而不是类型：

```sql
-- 该加的索引（消息上万条后全表扫描会慢）
CREATE INDEX idx_messages_session ON messages(session_id);
```

### 8.3 PostgreSQL 能否同时存业务数据和向量？

能。PostgreSQL + pgvector 插件可以在同一张表里混用普通列和向量列：

```sql
CREATE EXTENSION vector;
CREATE TABLE knowledge_base (
    id       SERIAL PRIMARY KEY,
    content  TEXT,              -- 业务数据
    source   TEXT,              -- 来源 URL
    embedding vector(1536),     -- OpenAI embedding（向量列）
    created_at TIMESTAMP DEFAULT NOW()
);

-- 同一张表：业务查询 + 向量相似度查询都能做
SELECT content, 1 - (embedding <=> query_vec) AS similarity
FROM knowledge_base
ORDER BY embedding <=> query_vec
LIMIT 5;
```

### 8.4 多用户多部门下的隔离层级

一个 `session_id` 不够。智能园区场景需要 4 层：

```
campus_id         ← 园区（物理边界）
tenant_id          ← 租户/企业（权限边界，公共区域可为 NULL）
user_id            ← 用户
conversation_id    ← 会话
```

| 场景 | 最少层级 |
|------|:--:|
| 个人项目 | 1层 `conversation_id` |
| 多用户 SaaS | 3层 `tenant` + `user` + `conversation` |
| 智能园区 | 4层 `campus` + `tenant` + `user` + `conversation` |

### 8.5 `get_messages("none")` 的 `"none"` 是什么？

截断策略。`ConversationMemory` 支持三种：

| 值 | 策略 | 行为 |
|---|------|------|
| `"none"` | 不截断 | 返回全部消息 |
| `"sliding_window"` | 滑动窗口 | 只保留最近 N 条 |
| `"token_limit"` | Token 限制 | 从最新倒序加，直到超 token 上限 |

### 8.6 `@property` 的缓存问题

`messages` 是 `@property`，每次访问都执行一次 SELECT：

```python
h.messages  # SELECT → 读库
h.messages  # SELECT → 又读一次库！
```

看着像廉价取值，实际每次 IO。生产环境应在调用方缓存一份，而非反复调 property。等价于 Java 的 `getMessages()` 每次查库——没有 L1 cache 的 JPA。

## 八-A、上下文压缩策略（Day5 补充）

Day5 补全的两级压缩系统，替代原来简单的截断策略。

### 8A.1 概述

```
原来（Day4）:                      现在（Day5 补充）:
  get_messages("token_limit")        compress_light()  ← 纯字符串，<1ms
  手动选择策略                        compress_heavy()  ← 调LLM，~1s
                                     auto_compress()   ← 自动阈值判断
```

### 8A.2 轻量压缩 `compress_light()`

触发阈值：上下文窗口 **10%**，<100ms，不调 LLM。

三步操作：
1. **剔除失败工具调用** — 含 "Error"/"失败"/"TypeError" 的 tool 消息直接丢弃
2. **口语化改写** — "那个啥，帮我算一下" → "算一下"，去掉口语冗余前缀
3. **合并同类消息** — 连续 tool 结果合并为一条，减少消息条数

```python
# 使用
mem = ConversationMemory()
msgs = mem.compress_light()  # 默认取全部消息
# 9条→8条, 179→153tokens, 0.0ms
```

### 8A.3 重量压缩 `compress_heavy()`

触发阈值：上下文窗口 **70%**，~1s，调 LLM 做摘要。

步骤：
1. 先做轻量清理
2. 提取"目标 + 关键结果"，丢弃中间过程和失败尝试
3. 调用 LLM 生成 200 字以内摘要
4. 输出：`[对话摘要] ...` 单条消息 + 保留 system prompt

```python
mem = ConversationMemory()
llm = LLMClient()
result = mem.compress_heavy(llm=llm)
# 9条→2条, 179→50tokens (节省129), 1305ms
```

### 8A.4 自动压缩 `auto_compress()`

根据 `_usage_ratio()` 自动判断：

```
< 10%  → None（不触发）
10-70% → compress_light()
> 70%  → compress_heavy()
```

## 八-B、Prompt 三层组装（Day5 补充）

借鉴 Hermes Agent 的分层架构，替代硬编码字符串。

### 8B.1 架构

```
stable 层 — 缓存，对话中不变
  ├─ 人格: "你是 ReAct Agent..."
  ├─ 工具指导: "calculator: 计算数学表达式"
  └─ 行为规则: "1. 计算问题必须调 calculator"

context 层 — 可刷新
  ├─ 用户偏好: "简短回答"
  └─ 项目信息: "agent-from-scratch-plus"

volatile 层 — 每次动态生成
  ├─ 当前时间: "2026-06-17 17:54"
  └─ 预算警告: "剩余迭代: 7/10"
```

### 8B.2 使用

```python
from src.prompt_builder import PromptBuilder

pb = PromptBuilder()
pb.set_personality("你是 ReAct Agent")
pb.add_tool_guidance("calculator", "计算")
pb.add_rule("计算问题必须调 calculator")
pb.load_context("用户偏好简短回答")

# 第一次 build → 构建 stable 层并缓存
prompt = pb.build("剩余3步")

# 第二次 build → stable 层缓存命中，只拼 volatile
prompt = pb.build("剩余2步")  # 更快，不重建
```

### 8B.3 Java 对照

```java
// Java 等价
class PromptBuilder {
    private String personality;    // stable
    private List<String> context;  // context
    private String cachedStable;   // 缓存

    String build(String budget) {
        if (dirty || cachedStable == null) {
            cachedStable = buildStable();  // 重建
        }
        return cachedStable + "\n" + buildContext() + "\n" + buildVolatile(budget);
    }
}
```

## 九、核心概念回顾

| 概念 | 一句话解释 |
|------|-----------|
| `SQLiteChatMessageHistory` | 消息的 SQLite 持久化存储，接口同 InMemory |

| `PromptBuilder` | 三层组装：stable（缓存）+ context（可刷新）+ volatile（动态） |

## 十、面试准备

**Q：InMemory 和 SQLite 持久化有什么区别？**
> InMemory 存在进程内存里，进程重启丢失。SQLite 存在磁盘上，重启后可恢复。Day5 的 SQLiteChatMessageHistory 实现了与 InMemoryChatMessageHistory 完全相同的接口（add_message / messages / clear），通过 ConversationMemory 的 history_backend 参数切换后端。策略模式。

**Q：多会话怎么隔离？**
> 每个消息行都有 session_id 字段。所有查询都带 `WHERE session_id = ?`，不同会话的消息互不可见。SessionManager 维护一个活跃会话 ID（active_session_id），get_history() 默认返回活跃会话的消息。

**Q：成本追踪怎么实现的？**
> 每次 LLMClient.chat() 返回的 dict 里包含 usage（prompt_tokens / completion_tokens / total_tokens）。SessionManager.record_usage() 把这组数据写入 token_usage 表。get_cost_stats() 用 SQL 聚合查询统计总消耗。
