## 二、模块逐项对照

### 2.1 Agent 循环引擎

| 维度 | Hermes Agent | 我们 | 差距 |
|------|-------------|------|:--:|
| 循环实现 | `AIAgent.run_conversation()` | `DynamicAgent.run()` → `graph.compile().invoke()` | 小 |
| 循环表达 | while 循环 + 条件 | LangGraph add_conditional_edges | — |
| 消息格式 | OpenAI `role/content/tool_calls` dict | 同 | ✅ |
| 多 provider | 18+ providers, 3 API modes | 单一 DeepSeek | 大 |
| 中断支持 | `_interruptible_api_call()` + 线程+事件 | 同步阻塞，不可中断 | 大 |
| 迭代预算 | 90 次，父子独立预算 | 10 次硬编码 | 小 |
| 模型降级 | 自动 fallback provider 链 | Day3 仅重试，不换模型 | 中 |

**核心差异：** 我们用的是 LangGraph 图表达循环，Hermes 是 while 循环。两者本质一样——都是"调 LLM → 解析 tool_calls → 执行 → 循环"。LangGraph 的优势在于可视化、checkpoint 暂停恢复。Hermes 的优势在于细粒度控制（中断、回调、预算）。

**代码级对比：**

```python
# Hermes Agent: while 循环 + 线程中断
# run_agent.py — _run_agent_loop()
while iteration_budget.remaining():
    response = self._interruptible_api_call(messages)  # 可被 Ctrl+C 中断

    if response.tool_calls:
        for tc in response.tool_calls:
            result = handle_function_call(tc)  # 支持 ThreadPoolExecutor 并发
            messages.append({"role": "tool", "content": result})
        continue  # ← 回到循环头
    else:
        return self._finalize(response)  # ← 结束

# 我们的 Day5: LangGraph 图
# dynamic_agent.py — build_dynamic_graph()
graph.add_conditional_edges(
    "agent",
    should_continue,                      # ← LLM 的 tool_calls 决定走哪
    {"tools": "tools", "end": END},
)
graph.add_edge("tools", "agent")          # ← 工具执行后自动循环

# 本质完全一样。一个是 while+if 表达，一个是图节点+边表达。

### 5.2 中断式 API 调用（详细解释）

```python
# Hermes Agent 的中断原理
# run_agent.py — _interruptible_api_call()

import threading

class AIAgent:
    def _interruptible_api_call(self, messages):
        self._interrupt_event = threading.Event()  # ← 中断信号
        result_holder = [None]

        def api_thread():
            """后台线程：发 HTTP，等 LLM 回复"""
            try:
                result_holder[0] = self._provider.chat(messages)
                self._interrupt_event.set()  # 通知主线程：完成了
            except Exception as e:
                result_holder[0] = e

        t = threading.Thread(target=api_thread)
        t.start()

        # 主线程等待两个信号之一：
        #   A) API 返回 → result_holder 有值
        #   B) 用户按 Ctrl+C → interrupt_event 被设置
        while not self._interrupt_event.is_set():
            if user_pressed_ctrl_c():
                return None  # 放弃等待，API 线程自行结束

        return result_holder[0]
```

**为什么我们没做：**
- LangGraph 的 `invoke()` 是同步阻塞的，没有内置中断
- 生产场景需要：用户发新消息 → 放弃当前 LLM 请求 → 立即响应新问题
- SAA 中你提到的"停止 LLM 输出"——OpenAI SDK 的 `stream` 模式可以在收到足够内容后 `break`，本质也是中断

**教学阶段够用，但面试可以讲这个设计。**

## 十、高并发 text2sql 场景（万人同时访问）

### 10.1 问题

```
10000+ 用户同时问 "本月销售额是多少"
  → 10000 个 LLM 请求生成 SQL
  → 10000 个 DB 查询
  → 10000 个 LLM 请求解释结果
  → 数据库扛不住，LLM API 限流
```

### 10.2 架构

```python
# ── 入口层：FastAPI + 异步 + 限流 ──
from slowapi import Limiter
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)

@app.post("/api/text2sql")
@limiter.limit("100/minute")  # 每用户每分钟100次
async def text2sql(req: Text2SQLRequest):
    # 推入队列，立即返回 task_id
    task_id = await redis.lpush("text2sql:queue", req.json())
    return {"task_id": task_id, "status": "queued"}

# ── Worker 层：消费队列 + Agent 执行 ──
async def worker():
    while True:
        # 阻塞等待任务
        _, task_json = await redis.brpop("text2sql:queue", timeout=5)

        task = Text2SQLRequest.parse_raw(task_json)

        # 每个 worker 有独立 Agent 实例
        agent = create_agent()  # Day3 工厂模式

        try:
            # LLM 生成 SQL
            sql = await agent.run(f"生成SQL: {task.question}")
            # 数据库查询（走连接池 + 只读副本）
            result = await db_pool.fetch(sql)  # 读副本
            # LLM 解释结果
            answer = await agent.run(f"解释: {result}")
            await redis.set(f"result:{task.id}", answer)
        finally:
            agent.clear()  # 清理上下文，复用实例

# ── 数据库层：读写分离 + 连接池 ──
from sqlalchemy.ext.asyncio import create_async_engine

# 主库（写）
master_engine = create_async_engine(
    "postgresql+asyncpg://user:pass@master:5432/db",
    pool_size=20,        # 最多 20 个连接
    max_overflow=10,     # 额外 10 个溢出连接
)

# 只读副本（读）
readonly_engine = create_async_engine(
    "postgresql+asyncpg://user:pass@replica:5432/db",
    pool_size=50,        # 读连接池更大
    max_overflow=20,
)

# ── 缓存层：相同问题走缓存 ──
async def cached_text2sql(question: str) -> str:
    cache_key = f"sql:{hashlib.md5(question.encode()).hexdigest()}"
    cached = await redis.get(cache_key)
    if cached:
        return cached  # 命中缓存，不调 LLM

    result = await run_agent(question)
    await redis.setex(cache_key, 300, result)  # 缓存5分钟
    return result
```

### 10.3 关键优化点

| 优化 | 效果 | 实现 |
|------|------|------|
| 异步队列 | 削峰，不丢请求 | Redis BRPOP |
| 连接池 | 控制 DB 并发 | SQLAlchemy pool_size |

## 十一、LangChain 的流中断 vs Disposable.dispose()

### 11.1 Java 端（Spring WebFlux）

```java
// Project Reactor — 取消订阅即中断
Flux<String> stream = aiPlatformClient.streamQuery("SELECT ...");
Disposable disposable = stream.subscribe(
    chunk -> System.out.println(chunk),
    error -> log.error("failed", error),
    () -> log.info("complete")
);

// 用户点了"停止"按钮
disposable.dispose();  // ← 取消订阅，底层 HTTP 连接关闭，LLM 停止生成
```

**原理：** Reactive Streams 的背压机制。`dispose()` 发送 `cancel` 信号，上游（SSE/HTTP）检测到后关闭连接。

### 11.2 Python 端（LangChain）

LangChain **没有** 内置的 Disposable 等价物，但有三种模式：

```python
# ── 方案1: asyncio 超时（最接近 Disposable）──
import asyncio

async def stream_with_timeout():
    agent = create_agent()
    try:
        # 30秒超时 → 自动取消
        result = await asyncio.wait_for(
            agent.llm.ainvoke(messages),  # LangChain 原生 async
            timeout=30.0
        )
    except asyncio.TimeoutError:
        # 超时 → asyncio 内部发送 CancelledError → 底层连接关闭
        return "请求超时，已中断"

# ── 方案2: threading.Event 手动中断 ──
import threading

class CancelableAgent:
    def __init__(self):
        self._cancel_event = threading.Event()

    def cancel(self):
        """用户点停止 → 设置事件"""
        self._cancel_event.set()

    def run(self, prompt):
        # 在后台线程跑 LLM 调用
        result_holder = []
        def _call():
            try:
                result_holder.append(self.llm.chat(prompt))
            except Exception:
                pass

        t = threading.Thread(target=_call)
        t.start()

        # 轮询检查是否被取消
        while t.is_alive():
            if self._cancel_event.is_set():
                # 无法真正 kill 线程，但可以放弃等待
                return "已取消"
            t.join(timeout=0.1)

        return result_holder[0] if result_holder else "无结果"

# ── 方案3: 流式 + break（最简单）──
async for chunk in agent.llm.astream(messages):
    if user_clicked_stop():
        break  # ← 等同于 dispose()
    yield chunk
```

### 11.3 对照总结

| Java (WebFlux) | Python (LangChain) | 说明 |
|----------------|-------------------|------|
| `Disposable.dispose()` | `asyncio.Task.cancel()` | 取消异步任务 |
| `Flux.takeUntil()` | `break` in async for | 条件中断 |
| `Mono.timeout()` | `asyncio.wait_for()` | 超时中断 |
| `Subscription.cancel()` | `threading.Event.set()` | 手动信号中断 |

**关键：** Python 的 `break` 在 `async for` 里就是 `Disposable.dispose()` —— 停止消费上游。而 `asyncio.wait_for()` 的超时机制是生产环境最常用的 LangChain 中断方式。
