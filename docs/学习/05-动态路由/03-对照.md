## 二、模块逐项对照

### 2.1 Agent 循环引擎

| 维度 | Hermes Agent | 我们 | 差距 |
|------|-------------|------|:--:|
| 循环实现 | `AIAgent.run_conversation()` | `DynamicAgent.run()` → `graph.compile().invoke()` | 小 |
| 循环表达 | while 循环 + 条件 | LangGraph add_conditional_edges | — |
| 消息格式 | OpenAI `role/content/tool_calls` dict | 同 | ✅ |
| 多 provider | 18+ providers, 3 API modes | 单一 DeepSeek | 大 |
| 中断支持 | `_interruptible_api_call()` + 线程+事件 | 同步阻塞，不可中断 | 大 |
| 迭代预算 | 90 次，父子独立预算 | 10 次硬编码 | 小 |
| 模型降级 | 自动 fallback provider 链 | Day3 仅重试，不换模型 | 中 |

**核心差异：** 我们用的是 LangGraph 图表达循环，Hermes 是 while 循环。两者本质一样——都是"调 LLM → 解析 tool_calls → 执行 → 循环"。LangGraph 的优势在于可视化、checkpoint 暂停恢复。Hermes 的优势在于细粒度控制（中断、回调、预算）。

**代码级对比：**

```python
# Hermes Agent: while 循环 + 线程中断
# run_agent.py — _run_agent_loop()
while iteration_budget.remaining():
    response = self._interruptible_api_call(messages)  # 可被 Ctrl+C 中断

    if response.tool_calls:
        for tc in response.tool_calls:
            result = handle_function_call(tc)  # 支持 ThreadPoolExecutor 并发
            messages.append({"role": "tool", "content": result})
        continue  # ← 回到循环头
    else:
        return self._finalize(response)  # ← 结束

# 我们的 Day5: LangGraph 图
# dynamic_agent.py — build_dynamic_graph()
graph.add_conditional_edges(
    "agent",
    should_continue,                      # ← LLM 的 tool_calls 决定走哪
    {"tools": "tools", "end": END},
)
graph.add_edge("tools", "agent")          # ← 工具执行后自动循环

# 本质完全一样。一个是 while+if 表达，一个是图节点+边表达。

### 2.2 工具系统

| 维度 | Hermes Agent | 我们 | 差距 |
|------|-------------|------|:--:|
| 工具数量 | 70+ 个，28 toolsets | 2 个（calculator, search_knowledge） | 大 |
| 注册方式 | `tools/*.py` import 时自动注册 | `TOOL_REGISTRY` 全局字典 | ✅ |
| 执行后端 | Terminal(6), Browser(5), Web(4), MCP | 单一本地函数调用 | 大 |
| 并行执行 | ThreadPoolExecutor 并发 | Day2 asyncio.gather | 小 |
| 危险命令检测 | `approval.py` + approval_callback | 无 | 大 |
| Agent 级工具 | todo, memory, delegate_task 拦截 | 无 | 大 |

**核心差异：** 我们证明了"自注册模式"的正确性（`tools/registry.py` 跟我们的 `TOOL_REGISTRY` 思路一样），但工具数量和执行后端差距巨大。Hermes 的 Terminal 支持 6 种后端（local/docker/ssh/daytona/modal/singularity），这是生产级多环境隔离。

**代码级对比：**

```python
# Hermes Agent: import 时自动注册
# tools/file_tools.py
from tools.registry import registry

def read_file(path, offset, limit):
    ...  # 实现

registry.register(
    name="read_file",
    func=read_file,
    description="Read a text file with line numbers",
    parameters={...}
)

# 我们的 Day1: 全局字典手动注册
# tools.py
TOOL_REGISTRY = {}

def calculator(expression: str) -> str:
    ...

TOOL_REGISTRY["calculator"] = {
    "function": calculator,
    "definition": {"name": "calculator", "description": "执行数学计算", ...}
}

# 同一个模式——自注册 + 中央注册表。我们的是教学简化版。
```

### 2.3 记忆与上下文

| 维度 | Hermes Agent | 我们 | 差距 |
|------|-------------|------|:--:|
| 消息存储 | SQLite + FTS5 全文搜索 | Day5 SQLiteChatMessageHistory | 小 |
| 持久化记忆 | MEMORY.md / USER.md 文件 | ⬜ | 中 |
| 上下文压缩 | 50%触发自动压缩 + 损失摘要 | ConversationMemory 截断策略 | 中 |
| Token 计数 | tiktoken | tiktoken（Day4） | ✅ |
| 会话恢复 | /resume 命令 | SessionManager.switch() | ✅ |
| 记忆系统 | MemoryManager + Provider ABC | ⬜ | 大 |
| 上下文引擎 | ContextEngine ABC（可插拔） | ⬜ | 大 |

**核心差异：** 我们的 SQLite 方案架构正确（Hermes 也用 SQLite），但缺少两个关键设计：
1. **ABC 抽象**：Hermes 的 MemoryProvider 和 ContextEngine 是抽象基类，可插拔。我们的 `ConversationMemory.history_backend` 参数是第一步，但还没做正式的 Provider 模式。
2. **自动压缩**：Hermes 在超过 50% 上下文窗口时自动触发压缩。我们只有手动截断策略。

**代码级对比：**

```python
# Hermes Agent: ABC + SQLite + FTS5
# agent/memory_provider.py
class MemoryProvider(ABC):
    @abstractmethod
    def load(self) -> str: ...
    @abstractmethod
    def save(self, content: str) -> None: ...

# hermes_state.py — 会话持久化
class SessionStore:
    def save_messages(self, session_id, messages):
        # SQLite + FTS5 全文索引
        ...

# 我们的 Day5: 直接 SQLite（无 ABC 抽象层）
# memory.py
class SQLiteChatMessageHistory:
    def add_message(self, msg):
        conn.execute(
            "INSERT INTO messages (session_id, role, content) VALUES (?, ?, ?)",
            (self.session_id, role, content)
        )

# 我们的架构方向对（SQLite），但缺少 ABC 抽象层。
# history_backend 参数是 Provider 模式的雏形。
```

### 2.4 提示词系统

| 维度 | Hermes Agent | 我们 | 差距 |
|------|-------------|------|:--:|
| 结构 | 3层：stable → context → volatile | 单层硬编码字符串 | 大 |
| 记忆注入 | 自动注入 MEMORY.md + USER.md | 手动 set_system() | 中 |
| Skills 注入 | 按需加载 SKILL.md | ⬜ | 大 |
| Anthropic 缓存 | prompt_caching.py 管理断点 | ⬜ | 大 |

**核心差异：** Hermes 的 prompt 是分层组装的——stable 层（人格+工具指导）不变，context 层（记忆文件）按需加载，volatile 层（时间戳+预算警告）每次动态生成。我们一个字符串搞定，这在教学阶段够用，但生产环境需要分层管理。

**代码级对比：**

```python
# Hermes Agent: 3层分层组装
# agent/prompt_builder.py
def build_system_prompt():
    parts = []

    # stable 层：人格 + 工具指导 + Skills（对话中不变）
    parts.append(PERSONALITY_PROMPT)
    parts.append(build_tool_guidance(active_tools))
    parts.append(build_skills_context(skills))

    # context 层：上下文文件 + 记忆文件（按需加载）
    parts.append(load_agents_md())           # AGENTS.md
    parts.append(memory_provider.load())     # MEMORY.md

    # volatile 层：时间戳 + 预算警告（每次动态）
    parts.append(f"Current time: {now()}")
    if budget.near_limit():
        parts.append("⚠️ 接近迭代上限，请尽快总结")

    return "\n\n".join(parts)

# 我们的 Day5: 单层硬编码字符串
# dynamic_agent.py — agent_node()
system_msg = {
    "role": "system",
    "content": (
        "你是 ReAct Agent。你有以下工具可用：calculator、search_knowledge。\n"
        "规则：\n"
        "1. 计算类问题 → 必须调 calculator\n"
        "2. 知识类问题 → 必须调 search_knowledge\n"
    )
}

# 差距：我们的是单层字符串，没有分层管理。
# Day6 建议：至少加 stable + volatile 两层。
```

## 五、我们能从 Hermes Agent 学到什么

### 5.1 架构层面（可以直接学）

**① Prompt 分层组装**

```
stable 层（不变）：  人格 + 工具指导 + Skills 描述
context 层（可变）：  上下文文件（AGENTS.md, CLAUDE.md）+ 记忆文件（MEMORY.md）
volatile 层（临时）： 时间戳 + 预算警告 + 上下文压力提示
```

我们在 Day5 还是单层字符串，Day6 可以加一层最简单的分层。

**② ABC 插拔模式**

```python
# Hermes 的做法
class MemoryProvider(ABC):
    def load(self) -> str: ...
    def save(self, content: str): ...

# 我们的 ConversationMemory.history_backend 参数是第一步
# 但还没抽象成正式 Provider 模式
```

**③ 中断式 API 调用**

```python
# Hermes: 主线程等待，后台线程发 HTTP
# 用户按 Ctrl+C → 设置 interrupt_event → 主线程检测到 → 放弃 API 线程
```

这个在当前教学阶段不需要，但生产环境非常重要——不能让一个慢响应 LLM 调用卡住整个系统。

### 5.2 设计哲学层面

| 原则 | 含义 | 我们做得如何 |
|------|------|:--:|
| Prompt stability | 系统提示词对话中不变 | 我们也是（set_system 只在开始时调） |
| Observable execution | 每个工具调用对用户可见 | 我们有 print 但没正式 callback |
| Interruptible | API 和工具执行可被取消 | ⬜ |
| Platform-agnostic | 一个 AIAgent 服务所有入口 | 我们的 DynamicAgent 只服务于 Python |
| Loose coupling | 可选子系统通过注册表模式 | 我们的 history_backend 参数是雏形 |
| Profile isolation | 多 profile 独立运行 | ⬜ |

## 七、关键认知

> **Hermes Agent 不是一个"比你写得好的 LangGraph 图"。它是一个完整的 Agent 操作系统。**
>
> 你的 Day5 两个阶段做的事情——动态路由图 + SQLite 持久化——恰好是它的核心骨架。剩下的 12 倍代码是"生态层"：20 个消息平台、6 种终端后端、5 种浏览器后端、18 个 provider、插件系统、完整 CLI。
>
> 你正在从教学版走向一个正确的架构方向。差距不在"会不会写"，而在"有没有落到生产"。
