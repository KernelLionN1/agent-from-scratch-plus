## 阶段一：LLM 动态路由（3h）

> 状态：✅ 完成  |  时间：2026-06-17  |  产出：`src/dynamic_agent.py`、`test/test_day5_phase1.py`

### 做了什么

**1.1 核心设计：从固定边到 LLM 自主决策**

Day4 的 LangGraph 图是固定工作流：`planner → coder → reviewer → END`，边的方向是程序员写死的。
Day5 的核心变化：LLM 通过 `tool_calls` 的有无决定下一步去哪。

图结构：
```
     ┌──────────────────┐
     │                  ↓
  agent ──(LLM判断)──→ tools ──→ agent (循环)
     │
     └──→ END (LLM 认为够了)
```

- `should_continue()` 函数只看 `state["messages"][-1]` 是否有 `tool_calls`
- 没有 if/else 硬编码规则，LLM 的返回本身决定了图的走向
- 与 OpenHarness 的 Agent Loop Engine 概念一致

**1.2 核心产出：`src/dynamic_agent.py`（294 行）**

| 组件 | 行数 | 说明 |
|------|:--:|------|
| `AgentState` | 31-39 | 图状态定义，messages + tool_results 用 `Annotated[list, add]` 自动追加 |
| `agent_node()` | 45-102 | Agent 节点：构建消息→调 LLM→返回 messages+步数 |
| `tool_node()` | 105-144 | 工具执行节点：解析 tool_calls→执行→返回结果 |
| `should_continue()` | 147-171 | 路由函数：LLM 的 tool_calls → "tools" 或 "end" |
| `build_dynamic_graph()` | 179-216 | 图构建：注册节点→条件边→循环边 |
| `DynamicAgent` | 223-264 | 对外的 Agent 类，封装图编译和调用 |

**1.3 踩坑发现与修复（2 个踩坑）**

| # | 踩坑 | 位置 | 现象 | 修复 |
|---|------|------|------|------|
| 1 | `state["input"]` 未传给 LLM | `agent_node:60-68` | LLM 只收到 system prompt，不知道用户问了什么 → 不调工具 | `messages` 为空时从 `state["input"]` 加 user 消息 |
| 2 | DeepSeek 的 kwargs 包装 | `tool_node:130-135` | 首次 tool_call 的 arguments 是 `{"kwargs": {"expression": "..."}}` → TypeError | 检测单键 `kwargs` 包装时自动解包 |
| 3 | `tool_results` 不用 `Annotated[list, add]` | `AgentState:35` | 多轮工具执行时 `tool_results` 被覆盖而非追加 | 改为 `Annotated[list, add]` |

### 决策记录

- `DynamicAgent.run()` 每次调 `graph.compile()` 而非缓存图，因为教学阶段优先代码清晰度
- 工具参数解包用"检测单键 `kwargs`"而非深度解析，覆盖 DeepSeek 特有格式
- 测试 1c 不强制 LLM 不调工具（用 `print` 而非 `assert`），因为不同 LLM 行为不同

### 做了什么

**2.1 SQLiteChatMessageHistory（`src/memory.py`）**

- 新增持久化消息存储类，接口与 InMemoryChatMessageHistory 完全一致
- 3 张表：`messages`（消息）、`sessions`（会话）、`token_usage`（成本）
- ConversationMemory 新增 `history_backend` 参数，可插拔切换 InMemory / SQLite

**2.2 SessionManager（`src/session.py`）**

- 会话 CRUD：`create()` / `switch()` / `list_sessions()` / `delete()` / `rename()`
- 成本追踪：`record_usage()` 记录每次 LLM 调用的 token → `get_cost_stats()` 聚合查询
- 便捷方法：`get_memory()` 一步获取带截断策略的 ConversationMemory
- `get_history()` 返回 SQLiteChatMessageHistory，默认取活跃会话

### 决策记录

- SQLiteChatMessageHistory 接收 dict 和 LangChain Message 两种格式

- `record_usage()` 对空 usage 静默跳过

### Day5 补充实现

> 上下文压缩 + Prompt 三层组装

- **compress_light()** — 剔除失败工具 + 口语化改写 + 合并同类，<1ms
- **compress_heavy()** — 调 LLM 生成摘要，~1s 但压缩率极高（9→2条）
- **auto_compress()** — 10%/70% 阈值自动选择
- **PromptBuilder** — stable(缓存) + context(可刷新) + volatile(动态)

## 阶段三：OpenHarness 对照分析（2h）

> 状态：✅ 完成  |  时间：2026-06-17  |  产出：`docs/学习/05-动态路由/03-对照.md`

### 做了什么

基于 Nous Research Hermes Agent 官方架构文档，逐模块对标我们的项目：

| 对比维度 | 我们 | Hermes |
|---------|------|--------|
| Agent 循环 | LangGraph StateGraph（301行） | while + 线程事件（4400行） |
| 工具系统 | 2 tools, 本地函数 | 70+ tools, 6种Terminal/5种Browser后端 |
| 记忆 | SQLiteChatMessageHistory | SQLite + FTS5 + MEMORY.md |
| 提示词 | 单层硬编码字符串 | 3层分层组装（stable/context/volatile） |
| 网关 | FastAPI HTTP | 20个消息平台适配器 |

### 核心发现

1. 架构方向正确：SQLite 持久化、Agent Loop 循环、工具注册模式都与 Hermes 一致
2. 差距在"生态层"：12 倍代码差在 20 个消息平台、18 个 provider、6 种后端
3. 设计哲学对齐：Prompt stability、Observable execution、Loose coupling
4. 三个可立刻学的：Prompt 分层组装、ABC 插拔模式、回调机制替代 print

### 决策记录

- 对照对象锁定 Hermes Agent（非 HKUDS/OpenHarness），因为后者是 CLI 工具框架，前者是 Agent 操作系统
- Day6 重点：Prompt 分层 + 自动压缩 + MEMORY.md + 回调
