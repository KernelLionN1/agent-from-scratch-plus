## 阶段一：角色定义 + 消息总线

> 时间：2026-06-16  |  产出：`src/roles.py`、`src/message_bus.py`、`test_day2_phase1.py`、`docs/学习/02-原生多agent/01-学习.md`

### 做了什么

1. **`src/roles.py`** — 角色定义模块
   - `AgentRole` 枚举：PLANNER / CODER / REVIEWER
   - `ROLE_PROMPTS`：每个角色的 system prompt（刻意写得模糊）
   - `RoleConfig`：捆绑 role + prompt + temperature
   - Planner temperature=0.7（需要创造力），Coder/Reviewer=0.3（需要精确）

2. **`src/message_bus.py`** — 消息总线
   - `Message` dataclass：标准化消息格式（sender/receiver/type/content/id/timestamp）
   - `MessageBus` 类：send / broadcast / receive / receive_since / receive_by_type
   - 内部用 dict[str, list[Message]] 按接收方存储

3. **`test_day2_phase1.py`** — 5 项验证全部通过
   - 验证 1：角色定义完整性
   - 验证 2：消息基本收发 + 隔离性
   - 验证 3：【踩坑】消息重复消费确认
   - 验证 4：广播 + 过滤 + 增量拉取
   - 验证 5：统计信息

4. **`docs/学习/02-原生多agent/01-学习.md`** — 学习指南
   - 概念讲解 + 代码走读 + Java 对照表 + 3 个动手实验

### 踩坑确认

| 坑点 | 验证结果 | 代码位置 |
|------|---------|---------|
| 消息重复消费 | ✅ 确认：同 ID 消息被 receive() 多次返回 | `message_bus.py:receive()` |
| 角色 Prompt 模糊 | ✅ 预留：prompt 不含禁止越权的约束 | `roles.py:ROLE_PROMPTS` |

### 决策记录

- 消息总线用 dataclass 而非普通类 —— Python 3.7+ 标准，对应 Java record
- receive() 只读不删是有意设计，用于教学演示重复消费问题
- 角色 prompt 故意不写「只能...不能...」约束，等 Day3 收紧

## 阶段二：串行任务分发

> 时间：2026-06-16  |  产出：`src/agents/`、`src/orchestrator.py`、`test_day2_phase2.py`、`docs/学习/02-原生多agent/02-学习.md`

### 做了什么

1. **`src/agents/base.py`** — Agent 基类（模板方法模式）
   - 封装 LLM 调用、消息收发、角色配置
   - `execute()` 抽象方法 → 子类重写

2. **`src/agents/planner.py`** — Planner Agent

3. **`src/agents/coder.py`** — Coder Agent
   - 接收子任务 → LLM 生成代码
   - `fix_code()` 根据审核意见修复代码

4. **`src/agents/reviewer.py`** — Reviewer Agent
   - 接收代码 → LLM 审核 → 改进建议
   - 从 4 个维度审核：正确性、可读性、性能、安全性

5. **`src/orchestrator.py`** — 串行编排器
   - `run_serial()` 直接调用模式
   - `run_serial_with_bus()` 消息总线模式

6. **`test_day2_phase2.py`** — 6 项验证全部通过
   - 验证 1-3：结构测试（无网络）
   - 验证 4：LLM 调用（Planner 2854字 / Coder 1146字 / Reviewer 2149字）
   - 验证 5：串行编排完整流程（4 步全部执行成功）
   - 验证 6：【踩坑】Coder 越权确认 — Coder 回答了规划问题

### 踩坑确认

| 坑点 | 验证结果 | 代码位置 |
|------|---------|---------|
| 任务拆分不合理 | ✅ 预留：不约束拆分粒度 | `planner.py:execute()` |
| 角色越权 | ✅ 复现：Coder 回答了项目规划问题 | 验证 6 |

## 阶段三：并行执行 + 结果汇总

> 时间：2026-06-17  |  产出：`src/orchestrator.py`(新增并行模式)、`test_day2_phase3.py`

### 做了什么

1. **`orchestrator.py` 新增并行模式**
   - `_parse_subtasks()` — 正则拆分 Planner 输出为子任务列表
   - `_coder_async()` — 用 `asyncio.to_thread()` 包装同步 LLM 调用（模拟异步）

   - `run_parallel_no_await()` — 【踩坑演示】创建协程但不 await，全部丢弃
   - `run_parallel_with_timeout()` — `asyncio.wait_for` 超时后丢弃所有结果（踩坑）

2. **`test_day2_phase3.py`** — 6 项验证，5 通过 1 失败

| 验证 2：并行执行结构 | ✅ | 5 个方法全部存在，`_coder_async` 是 async 协程 |
| 验证 3：并行执行（真实 LLM） | ✅ | 2 个 Coder 并行 12.8s（串行预估 26s），结果正常汇总 |

### 踩坑确认

| 坑点 | 验证结果 | 代码位置 |
|------|---------|---------|
| 无等待逻辑 | ✅ 确认：run_parallel_no_await() 协程全部丢弃 | `orchestrator.py:386-393` |
| 输出格式不统一 | ✅ 确认：两个 Coder 输出格式有差异 | 验证 6 |
| 超时丢失部分结果 | ⬜ 预留：run_parallel_with_timeout() 超时后 return [] | `orchestrator.py:438-440` |

### 决策记录

- 每个 Coder 独立创建实例（避免共享 LLMClient 串行化），但 MessageBus 共享（体现通信模式）
- `_parse_subtasks` 的 bug 留到 Day3 统一修，符合项目约定
- 兜底机制（重试/熔断/部分结果收集）是 Day3 的核心内容，Day2 只暴露问题

## 阶段四：全局状态管理

> 时间：2026-06-17  |  产出：`src/shared_state.py`、`test_day2_phase4.py`、`orchestrator.py`(新增状态追踪模式)

### 做了什么

1. **`src/shared_state.py`** — 全局共享状态管理
   - 线程安全读写（`threading.Lock` 保护）
   - 乐观锁版本控制（类似 JPA `@Version`）：`update(key, val, expected_version)` 版本不匹配则拒绝
   - 深拷贝隔离：`get()` 返回 `deepcopy`，外部修改不污染内部
   - `init_progress()` / `mark_task_done()` / `record_error()` 便利方法
   - `bypass_lock()` 踩坑演示：绕过锁直接修改，版本号不递增

2. **`BaseAgent` 集成** — 新增 `shared_state` 属性（可选），Orchestrator 创建后注入

3. **`Orchestrator` 新增三个方法：**
   - `__init__(bus, with_shared_state=True)` — 创建 SharedState 并注入所有 Agent
   - `run_serial_with_state()` — 串行编排 + 每步记录进度到 SharedState
   - `run_parallel_with_state()` — 并行编排 + 追踪各 Coder 进度
   - `demonstrate_concurrent_conflict()` — 纯逻辑演示乐观锁冲突（不调 LLM）

4. **`test_day2_phase4.py`** — 8 项验证全部通过

### 测试结果

| 验证 | 结果 | 现象 |
|------|:---:|------|
| 1：共享状态基础读写 | ✅ | set/get/keys/has/default 全部正常 |
| 2：乐观锁版本控制 | ✅ | 版本匹配成功，不匹配拒绝（冲突计数 2） |
| 3：bypass_lock 踩坑 | ✅ | 值被覆盖但版本号不递增，乐观锁完全失效 |
| 4：深拷贝隔离 | ✅ | 嵌套 dict 也隔离，外部修改不影响内部 |
| 5：Orchestrator 并发冲突 | ✅ | 版本冲突检测正常，bypass 确认风险 |
| 6：串行编排+状态追踪 | ✅ | 4/4 步完成，state_snapshot 含 7 个键 |
| 7：并行编排+状态追踪 | ✅ | 3/3 阶段完成，2 Coder 并行 + 进度追踪 |
| 8：Agent 直接改全局 dict | ✅ | counter=1 不是 2，状态错乱确认（对比 SharedState 则安全） |

### 踩坑确认

| 坑点 | 验证结果 | 代码位置 |
|------|---------|---------|
| 全局变量滥用 | ✅ 确认：两个 Agent 无锁改全局 dict → counter 被覆盖 | 验证 8 |
| 状态错乱 | ✅ 确认：bypass_lock 绕过版本控制，乐观锁失效 | `shared_state.py:bypass_lock()` |
| 版本冲突无重试 | ✅ 确认：update() 返回 False，不做自动重试（留 Day3） | `shared_state.py:update()` |

### 决策记录

- SharedState 用 `threading.Lock` 而非 `asyncio.Lock`——因为 LLMClient 是同步的，Agent 执行在线程池里
- `get()` 返回深拷贝，防御外部修改污染——额外开销但教学上值
- Agent 通过 `shared_state` 属性注入而非构造参数——保持构造函数简洁，向后兼容阶段二/三
- `bypass_lock()` 故意不递增版本号，模拟真实"拿 _data 引用直接改"的踩坑场景
- Day3 应该补全：update() 失败时的自动重试 + 超时放弃 + 死锁检测
